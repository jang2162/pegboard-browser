# 2a단계 설계: MCP와 세션 정책

- 작성일: 2026-11-13
- 상태: 사용자 승인 (2026-11-13)
- 앞 문서: [architecture.md](../architecture.md) 7절(CLI와 MCP), 11절(보안), [roadmap.md](../roadmap.md) 2단계, [phase1-handoff/README.md](./phase1-handoff/README.md)
- 표기: "사용자 결정"은 2026-11-13 대화에서 사용자가 고른 것, "제안"은 작성자가 정했고 사용자가 아직 고칠 수 있는 것이다.

## 1. 왜 만드는가

1단계는 셸을 가진 사람이 `pegboard` CLI로 세션을 만들어 브라우저를 조종하는 데까지 왔다. 에이전트가 실제로 붙어 쓰려면 셸 없이도 쓸 수 있는 인터페이스가 필요하고, 그 인터페이스는 조종당한 에이전트가 할 수 있는 일을 사람이 미리 정한 범위로 묶어야 한다.

2단계 전체(roadmap.md)는 크다. 둘로 나눈다(사용자 결정).

- **2a (이 문서)**: `pegboard mcp`와 세션 정책.
- **2b (다음 문서)**: 화면 녹화, 재생, 보존 정책.
- 프로필 복사(`--from`, `--temp-profile`)는 2b 뒤로 미룬다(제안). 로그인 정보를 복제하는 일이라 따로 설계한다.

## 2. 목표, 하지 않는 것, 실패로 볼 것

**목표**

1. MCP 클라이언트 설정에 `pegboard mcp`를 넣으면, 셸이 없는 에이전트가 세션을 만들고 브라우저를 조종하고 자기 세션의 동작 기록을 읽을 수 있다.
2. MCP로 들어온 모든 브라우저 명령이 CLI와 같은 검사(허용 명령 문법, 비밀 가림, 동작 기록)를 거친다. 검사는 한 벌이다.
3. 세션마다 정책이 붙는다. 정책은 사람이 정하고 에이전트는 바꿀 수 없다.
4. 1단계에서 임시로 막아 둔 것(다운로드)과 열려 있던 것(내부망, 자기 포트, 클립보드, 쿠키 쓰기)을 정책으로 정리한다.

**하지 않는 것 (2a)**

- 화면 녹화와 재생, 보존 정책, 프로필 복사.
- 실시간 승인 화면. 브라우저 승인 창은 3단계(Chromium 포크)의 일이다.
- 원격(릴레이), 설치형 브라우저.
- 같은 사용자 계정의 셸을 가진 프로세스로부터의 보호. 1단계와 같이 "셸을 가진 에이전트는 사용자와 같다". 유닉스 소켓의 코어 API는 지금처럼 소유자 검사만 한다.

**실패로 볼 것** (하나라도 생기면 2a는 실패다)

- MCP 도구만 가진 에이전트가 사람 프로필의 탭이나 데이터, 다른 세션의 탭, 프록시 밖의 브라우저에 닿는다.
- 기본 모드의 MCP 에이전트가 자기가 만들지 않은 세션을 조종하거나 닫거나 그 기록을 읽는다.
- MCP 에이전트가 자기 세션의 정책을 넓힌다(허용 옵션, 도메인 허용목록, 내부망, 업로드 폴더).
- 세션 토큰이나 프록시 토큰이 도구 결과, 오류 문구, 동작 기록에 나온다.
- MCP로 들어온 명령이 CLI와 다른 검사 경로를 탄다.
- 동작 기록에 비밀이 평문으로 남는다(1단계 조건 유지).

|---|---|---|

## 4. 접근 방식

MCP 도구를 어떻게 구성할지 세 가지를 견주었다.

1. **agent-browser의 MCP 도구를 그대로 중계** (architecture.md의 초안). 도구 목록과 설명을 공짜로 얻는다. 하지만 요청이 JSON으로 들어와 agent-browser가 직접 해석하므로 1단계의 argv 검사와 비밀 가림을 거치지 않는다. 같은 검사를 JSON용으로 한 벌 더 만들고 두 벌을 맞춰 유지해야 한다.
2. **pegboard가 도구를 정의하고 argv로 바꿔 실행** (선택). 검사와 가림이 한 벌이고, "CLI와 MCP가 같은 결과"가 구조로 보장된다. 도구 설명을 우리가 써야 하고, agent-browser의 새 명령이 자동으로 따라오지 않는다.
3. **범용 도구 하나**(`pegboard_command`에 argv를 그대로 받는다). 가장 작다. 에이전트가 어떤 명령이 있는지 도구 목록으로 알 수 없고, 도구별 허용 여부를 보여 줄 수 없다.

2를 골랐다(사용자 결정 D6). 1단계에서 가장 공을 들인 것이 argv 검사인데 1은 그것을 우회하는 두 번째 입구를 만든다. architecture.md 7절의 "agent-browser의 MCP 도구 목록을 그대로 중계한다"는 이 문서로 대체한다.

## 5. 설계

### 5.1 `pegboard mcp`

- stdio MCP 서버. 같은 `pegboard` 바이너리의 하위 명령이다. 코어 API(유닉스 소켓)를 CLI와 같은 `Client`로 부른다.
- MCP 프로토콜은 `initialize`, `tools/list`, `tools/call`, `ping`만 지원한다. 리소스와 프롬프트는 없다. 프로토콜 구현을 직접 할지 크레이트를 쓸지는 만드는 쪽이 정한다.
- 데몬이 떠 있지 않으면 `pegboard mcp`가 `browser start`와 같은 방법으로 띄운다(제안). 셸 없는 에이전트는 띄울 방법이 없기 때문이다. 기본 모드에서는 브라우저를 끄는 도구가 없다.

**두 모드 (D1)**

| | 기본 모드 | `--operator` |
|---|---|---|
| 세션 만들기 | 된다. 정책은 5.3의 "MCP 서버 정책"으로 고정 | 된다. 정책을 인자로 줄 수 있다 |
| 볼 수 있는 세션 | 이 MCP 서버가 만들었거나 넘겨받은 세션만 | 전부 |
| 조종, 닫기, 기록 읽기 | 위 세션만 | 전부(핸들을 가진 세션. 아래 참고) |
| 프로필 | 이미 있는 프로필 이름을 골라 세션을 만들 수 있다. 목록 보기, 만들기, 삭제는 없다 | 목록, 만들기, 열기, 삭제 |
| 브라우저 끄기 | 없다 | 있다 |

- **세션 토큰은 모델에게 보이지 않는다.** MCP 서버 프로세스가 자기가 만든 세션의 핸들(`<id>.<token>`)을 메모리에 쥐고, 도구 인자와 결과에는 세션 ID만 쓴다. 기본 모드의 "자기 세션만"은 MCP 서버가 쥔 핸들 집합으로 강제한다.
- **권한 구분은 MCP 서버 프로세스가 한다.** 셸 없는 에이전트는 MCP 도구 말고는 닿을 길이 없다. 데몬 쪽 코어 API에는 호출자 구분을 넣지 않는다(2a의 범위 밖).
- **사람이 만든 세션 넘겨받기**: `pegboard mcp`를 띄울 때 `PEGBOARD_SESSION`(핸들)이 있으면 그 세션을 자기 세션으로 넘겨받는다. 사람이 CLI로 넓은 정책의 세션을 만들어 에이전트에게 주는 길이다.
- **`--operator`에서 다른 세션 조종**: 코어 API는 조종과 닫기에 토큰을 요구한다(1단계). 운영자 모드가 남의 세션을 다루려면 토큰이 필요하므로, 코어 API에 "운영자용으로 세션의 핸들을 다시 내주는" 메서드가 있어야 한다. 이 메서드는 소켓에 닿는 누구나 부를 수 있게 되는데, 이것은 1단계의 경계("소켓에 닿으면 사용자와 같다. `browser stop`도 토큰이 없다")와 같은 수준이다. 그래도 핸들이 흘러 다닐 길이 하나 늘어나므로, 만드는 쪽은 이 메서드 없이 가는 방법(예: 운영자 모드는 닫기와 기록 읽기만 남의 세션에 하고, 조종은 자기 세션만)과 견주어 더 좁은 쪽을 고른다(제안: 더 좁은 쪽. 운영자 모드에서 남의 세션은 목록 보기, 닫기, 기록 읽기만).
- **MCP 서버가 끝날 때**(stdio가 닫히거나 신호를 받음) 자기가 만든 세션을 닫는다(제안). 핸들이 메모리에만 있어서, 닫지 않으면 `browser stop`으로만 치울 수 있는 세션이 쌓인다. 넘겨받은 세션(`PEGBOARD_SESSION`)은 닫지 않는다. 사람이 만든 것이기 때문이다.

### 5.2 도구

**관리 도구** (이름은 제안)

| 도구 | 인자 | 기본 모드 | `--operator` |
|---|---|---|---|
| `pegboard_session_create` | `name?`, `url?`, `profile?` | 있음 | 있음 + 정책 인자(5.3) |
| `pegboard_session_list` | 없음 | 자기 세션만 | 전부 |
| `pegboard_session_info` | `sessionId` | 자기 세션만 | 전부 |
| `pegboard_session_close` | `sessionId`, `keepTabs?` | 자기 세션만 | 전부 |
| `pegboard_recording_list` | 없음 | 자기 세션의 기록만 | 전부 |
| `pegboard_recording_get` | `recordingId` | 자기 세션의 기록만 | 전부 |
| `pegboard_profile_list` / `_create` / `_open` / `_delete` | CLI와 같음 | 없음 | 있음 |
| `pegboard_browser_status` | 없음 | 있음 | 있음 |
| `pegboard_browser_stop` | 없음 | 없음 | 있음 |

**브라우저 동작 도구**

- 허용 명령 문법(`crates/pegboard-core/src/argv.rs`의 `GRAMMAR`)에서 만들어 낸다. 문법이 유일한 출처다: 도구 목록, 인자 스키마, argv로 바꾸는 규칙을 문법에서 생성하고, 문법에 명령을 더하면 도구가 따라 생긴다. 문법에 없는 것을 MCP가 받을 수 없어야 한다.
- 도구 하나가 명령의 첫 단어 하나에 대응한다(예: `pegboard_snapshot`, `pegboard_click`, `pegboard_get`, `pegboard_tab`). 하위 명령과 플래그는 인자로 받는다. 모든 동작 도구는 `sessionId`를 받는다(제안: 자기 세션이 하나뿐이면 생략할 수 있다).
- 호출이 오면: 인자를 argv로 바꾼다 → 코어 API `command.exec`에 CLI와 같은 꼴로 보낸다. 그 뒤는 1단계 경로 그대로다(`argv::check` → 정책 판정(5.3) → `runner.exec` → 동작 기록).
- 결과는 agent-browser의 출력을 그대로 텍스트로 돌려준다. 페이지에서 온 내용에는 경계 표식을 붙인다(roadmap 2단계 8번. agent-browser의 `AGENT_BROWSER_CONTENT_BOUNDARIES`가 이미 켜져 있는지 확인하고, MCP 결과에서 그 표식이 유지되게 한다).
- `screenshot`은 세션 파일 디렉터리에 저장한 뒤 MCP 이미지 콘텐츠로도 돌려준다(제안). 셸 없는 에이전트는 파일을 읽을 방법이 없다.
- 도구 설명은 우리가 쓴다. agent-browser의 도움말 문구를 참고하되, 설명에 세션 밖으로 나가는 방법을 암시하는 내용은 넣지 않는다.
- 도구 묶음: `--tools <묶음,...>`으로 노출할 도구를 줄일 수 있다(제안: `core`, `tabs`, `state`, `network`, `all`. 기본 `core,tabs`). 도구 목록은 MCP 서버 하나에 한 벌이고 세션이 생기거나 닫혀도 바뀌지 않는다. 정책이 막는 명령은 목록에서 빼지 않고 `policy_denied`로 답한다(제안: 정책은 세션마다 다르고 한 도구 안에 허용 형식과 거부 형식이 섞여 있어서(`cookies`의 읽기와 `cookies set`), 목록으로 가릴 수 없다).

**CLI와 MCP의 동등성** (roadmap 2단계 2번): 같은 세션에서 같은 명령을 CLI와 MCP로 실행하면 코어 API에 도착하는 argv가 같고, 동작 기록 항목이 같은 꼴이며, 거부되는 입력이 같다. 문법의 모든 형식에 대해 시험한다.

### 5.3 세션 정책

세션마다 정책 하나가 붙는다. 세션을 만들 때 정해지고 그 뒤로 바뀌지 않는다. 판정은 `pegboardd`가 한다(architecture.md 11절). 세 층이다.

1. **범위**: 자기 탭만. 프록시가 강제하고 정책으로 풀 수 없다(1단계).
2. **주소**: 어디로 갈 수 있는가.
3. **동작**: 어떤 종류의 명령을 할 수 있는가.

**정책을 정하는 곳**

- CLI: `pegboard session create`의 옵션.
- MCP 기본 모드: `pegboard mcp`를 띄울 때의 옵션("MCP 서버 정책"). MCP 클라이언트 설정 파일에 사람이 적는다. 그 서버가 만드는 모든 세션에 붙는다. 도구 인자로는 줄 수 없다.
- MCP `--operator`: `pegboard_session_create`의 인자로 줄 수 있다.

옵션 이름(제안, `session create`와 `mcp`에 같은 이름):

| 옵션 | 뜻 |
|---|---|
| `--allow <분류,...>` | 기본이 거부인 분류를 연다: `upload`, `state`, `clipboard` |
| `--deny <분류,...>` | 기본이 허용인 분류를 닫는다: `eval`, `download` 등 |
| `--allow-domain <도메인,...>` | 주소 허용목록. 주면 그 밖의 도메인으로 나가지 못한다 |
| `--allow-private-network` | 사설망 주소를 연다 |
| `--no-localhost` | `localhost`를 닫는다 |
| `--upload-dir <디렉터리>` | 업로드할 수 있는 파일이 있는 폴더(5.5) |

**동작 분류와 기본값**

분류는 우리가 명령 이름에서 직접 매핑한다(agent-browser의 정책 기능에 기대지 않는다. architecture.md 11절). 문법의 각 형식에 분류를 붙이고, 분류가 없는 형식은 컴파일이나 시험에서 걸리게 한다.

| 분류 | 기본 | 비고 |
|---|---|---|
| `navigate`, `click`, `fill`, `snapshot`, `scroll`, `wait`, `read`, `get`, `interact` | 허용 | |
| `eval` | 허용 | `--deny eval`로 닫는다 |
| `download` | 허용, 세션 디렉터리로만 | 5.4 |
| `upload` | 거부 | `--allow upload`와 `--upload-dir`이 둘 다 있어야 열린다 |
| `state` (쿠키와 저장소 쓰기) | 거부 | **1단계와 달라진다**: `cookies set`, `storage ... set`이 지금은 허용이다. 2a부터 `--allow state`가 필요하다 |
| `clipboard` | 거부 | D3. 5.6 |
| `network` (요청 가로채기, `network route`) | 2a에서는 문법에 넣지 않는다(제안) | 프록시의 Fetch 도메인 규칙을 따로 설계해야 한다 |

거부된 명령은 `argv_rejected`가 아니라 새 오류 코드 `policy_denied`로 끝나고, 어떤 분류가 왜 막혔는지와 여는 방법(사람이 세션을 만들 때 줄 옵션)을 한 줄로 알려 준다. 동작 기록에는 1단계의 거부 규칙대로 남긴다(명령 이름만, 인자는 가림).

**주소 규칙 (D2)**

판정 순서:

1. pegboard 자신의 포트(브라우저 디버깅 포트, 세션 프록시 포트): 항상 거부. 정책으로 풀 수 없다.
2. 스킴: 1단계대로 `http`, `https`, `data`, `about:blank`만.
3. `--allow-domain`이 있으면(D7): 목록의 도메인과 그 하위 도메인만 허용하고 나머지는 전부 거부한다. 루프백도 목록에 `localhost`(또는 그 주소)가 있어야 열린다. 사설망 주소는 목록에 있더라도 `--allow-private-network`가 함께 있어야 열린다. 아래 4와 5는 허용목록이 없을 때의 규칙이다.
4. 루프백(`localhost`, `127.0.0.0/8`, `::1`): 허용. `--no-localhost`면 거부.
5. 사설망(RFC 1918, 링크 로컬, CGNAT, IPv6 ULA와 링크 로컬): 거부. `--allow-private-network`면 허용.

적용 대상: 주 프레임과 하위 프레임의 탐색, 그리고 페이지가 내는 하위 요청(스크립트의 `fetch`, 이미지, 웹소켓 포함). 에이전트가 `eval`로 내는 요청도 막혀야 한다.

강제 방법: `pegboardd`가 자기 연결로 세션의 각 타깃에 요청 가로채기를 걸어 판정한다(roadmap의 "프록시 구현"). 에이전트 쪽 연결은 이 가로채기를 끄거나 바꿀 수 없어야 한다(프록시 필터가 이미 `Fetch.*`와 컨텍스트 없는 `Network.*`를 막는지 확인하고, 막지 않는 것이 있으면 막는다).

**이름이 사설 주소로 풀리는 경우**: 호스트 이름이 공개 이름이라도 사설 주소로 풀리면 5의 규칙을 적용해야 한다. 요청 단계에서는 이름만 보이므로, 응답이 도착했을 때의 실제 원격 주소로 한 번 더 판정해 본문이 페이지에 전달되기 전에 끊는다. 이 방법으로 막히지 않는 경우(요청 자체가 부작용을 내는 경우)는 "남는 위험"으로 문서에 적는다. 만드는 쪽은 먼저 작은 실험으로 Chrome이 이 판정에 필요한 정보를 어느 시점에 주는지 재고, 결과에 따라 방법을 정한다. 실험 결과가 이 절의 요구를 충족할 수 없다고 나오면 만들기를 멈추고 사용자에게 알린다.

**프로필 단위로만 걸리는 설정 (D8)**

정책은 세션마다 붙지만 Chrome이 프로필(브라우저 컨텍스트) 단위로만 걸게 해 주는 것이 있다. 클립보드 권한이 그렇고, 페이지가 등록한 서비스 워커와 공유 워커가 내는 요청의 주소 판정도 탭이 아니라 프로필에 속한다.

- 만드는 쪽은 각 정책 항목이 탭 단위로 강제되는지 프로필 단위로만 되는지 실험으로 가른다. 프로필 단위로만 되는 항목의 목록을 문서에 남긴다.
- 프로필 단위 항목은 그 프로필에 세션이 하나라도 있는 동안 고정된다. 값은 첫 세션의 정책이 정한다.
- 그 프로필에 다른 값을 원하는 세션을 만들려 하면 거절한다. 오류는 어떤 항목이 지금 어떤 값으로 고정돼 있는지와 "다른 프로필을 쓰라(`--profile`)"를 알려 준다.
- 그 프로필의 세션이 모두 닫히면 고정이 풀린다.
- 어떤 세션도 같은 프로필의 다른 세션 때문에 권한이 넓어지지 않아야 한다. 이것을 시험으로 보인다.

### 5.4 다운로드

1단계는 에이전트 프로필의 다운로드를 전부 막는다(임시 조치). 2a에서 "세션 디렉터리로만 허용"으로 바꾼다.

- 걸림돌(1단계에서 잰 것): 다운로드 정책은 프로필(브라우저 컨텍스트) 단위다. 한 프로필을 여러 세션이 같이 쓰므로 Chrome에게 세션별 폴더를 시킬 수 없다. 정책은 건 연결이 닫히면 사라지고, 한 연결은 컨텍스트 하나의 정책만 쥔다.
- 방법: 프로필마다 `pegboardd`만 아는 임시 폴더로 받게 하고(파일 이름은 Chrome이 붙이는 식별자), 다운로드가 어느 탭에서 시작됐는지로 세션을 찾아 그 세션의 파일 디렉터리(`<PEGBOARD_HOME>/sessions/<id>/files`)로 옮긴다. 어느 세션 것인지 알 수 없는 다운로드는 지운다. `--deny download`인 세션의 다운로드도 지운다.
- 한도(제안): 파일 하나 200 MiB, 세션 하나의 다운로드 합계 1 GiB. 넘으면 지우고 그 사실을 다음 명령의 결과와 동작 기록에 남긴다.
- 에이전트에게 보이는 것: 받은 파일의 이름과 크기를 알려 주는 도구나 명령이 필요하다(제안: `pegboard files list`와 대응하는 MCP 도구. 세션 파일 디렉터리의 목록만 보여 준다). 파일 내용을 에이전트에게 돌려주는 기능은 2a에 넣지 않는다.
- 세션을 닫으면 파일 디렉터리가 지워지는 1단계 동작은 그대로다. 사람이 가져가려면 닫기 전에 복사한다(README에 이미 있다).
- 1단계의 "차단" 연결이 끊겼을 때 다시 걸지 않는 틈(README의 알려진 한계)을 같이 메운다: 정책 연결이 끊기면 다시 걸고, 다시 걸릴 때까지 그 프로필의 세션은 명령을 받지 않는다.
- 사람 프로필의 다운로드에는 손대지 않는다(1단계 조건 유지).

### 5.5 업로드

- `--allow upload`와 `--upload-dir <디렉터리>`가 둘 다 있는 세션에서만 된다. 에이전트는 그 폴더 안의 파일을 맨 파일 이름으로만 고를 수 있다(1단계의 파일 이름 규칙과 같다: 경로 구분자, 심볼릭 링크, 폴더 밖을 가리키는 이름은 거부).
- 사람이 폴더를 정하므로, 조종당한 에이전트가 사용자의 임의 파일을 올릴 수 없다.
- 다운로드로 받은 파일을 다시 올리는 것(세션 파일 디렉터리에서 업로드)은 `--allow upload`만 있으면 되게 할지 만드는 쪽이 정한다(제안: 된다. 에이전트가 받은 것만 올릴 수 있으므로 새는 것이 없다).

### 5.6 클립보드 (D3)

- 에이전트 프로필의 페이지가 시스템 클립보드를 읽거나 쓰지 못하게 한다. `eval`로 `navigator.clipboard`를 부르는 것, `document.execCommand('copy')`, 키 입력(`press Meta+c`, `Meta+v`)이 모두 대상이다.
- 방법은 만드는 쪽이 실험으로 정한다(브라우저 컨텍스트의 권한 설정, 키 입력 조합의 거부 등). 실험에서 막을 수 없는 경로가 나오면 그 경로를 "남는 위험"에 적고 사용자에게 알린다.
- `--allow clipboard`로 연다.
- 사람 프로필의 클립보드 동작에는 손대지 않는다.

### 5.7 세션 닫기 (D4)

- 세션을 닫을 때 닫는 탭은 그 세션의 범위에 있는 탭(프록시가 아는 타깃)뿐이다. 자기 그룹 안에 있더라도 다른 세션의 범위에 있는 탭은 닫지 않는다.
- 자기 그룹 안에 있지만 어느 세션의 범위에도 없는 탭(사람이 그 그룹 안에 직접 연 탭)은 지금처럼 닫는다(제안. 그룹이 사라지는데 탭만 남으면 주인 없는 탭이 된다).

### 5.8 같이 고칠 것

1단계에서 넘어온 것 가운데 2a에 넣는 것:

- `pegboard tab new 'data:...'`가 성공으로 끝나지만 `about:blank`로 열린다.
- 입력 상한: `command.exec`의 인자 길이(문자열 하나, argv 전체), 한 MCP 서버가 만들 수 있는 세션 수(제안: 16), 동작 기록 한 줄의 크기. 셸 없는 에이전트가 반복 호출로 디스크나 메모리를 채우지 못하게 한다.
- `Client`가 시간 초과 뒤 같은 연결을 다시 쓰면 앞 요청의 응답을 받을 수 있다(1단계 최종 검토). MCP 서버는 연결을 오래 쓰므로, 응답 id를 확인하거나 시간 초과 뒤 연결을 버린다.
- 유휴 세션 만료(architecture.md 6절의 1시간): 핸들을 잃은 세션이 쌓이지 않게 넣는다(제안: 마지막 명령 뒤 1시간. `session create --no-expire`로 끈다).
- 사람이 닫은 탭이 그 세션의 `tab list`에 남아 보이는 것(프록시가 범위 밖이 된 타깃의 소멸 이벤트를 에이전트 쪽에 전하지 않는다).

2a에 넣지 않는 것: 브라우저 수준 자동 연결을 프록시가 흉내 내는 방식(별도 작업), 자식 프로세스의 파일 기술자 정리, 기록 보존 기간(2b).

### 5.9 시험

- **격리 시험 묶음에 MCP 판을 더한다.** `e2e_isolation`이 CLI로 하는 시도를 MCP 도구로도 한다. 더해서: 기본 모드에서 남의 세션 ID로 조종, 닫기, 기록 읽기가 거부된다. 정책을 넓히는 인자를 도구에 줘도 무시되거나 거부된다. 도구 결과와 오류에 토큰이 없다.
- **동등성 시험** (5.2).
- **정책 시험**: 분류별 허용과 거부, 주소 규칙의 각 순서, 사설 주소로 풀리는 이름, pegboard 자신의 포트, 다운로드의 세션 귀속과 한도, 업로드 폴더 밖의 파일.
- **시험이 브라우저를 덜 띄우게 한다.** 지금은 시험 하나마다 Chrome을 새로 띄운다(전체 한 번에 106번 이상). 격리 시험 묶음은 깨끗한 브라우저가 필요하므로 그대로 두고, 나머지는 시험 파일 하나가 브라우저 하나를 같이 쓰게 바꾼다. 이 작업을 2a의 첫 작업으로 한다. 시험이 늘기 전이 싸다. 바꾼 뒤에도 각 시험이 실패할 수 있음(바꾸기 전에 잡던 결함을 여전히 잡음)을 보인다.
- 실제 브라우저를 띄우는 시험은 두 번째 기기(맥미니)에서 돌리고, 코드 작업은 첫 번째 기기에서 한다(사용자 지시, 2026-11-13). 두 번째 기기는 작업을 조율하는 쪽(컨트롤러)만 닿을 수 있다(Orca의 원격 환경). 그래서 구현 에이전트는 코드와 브라우저 없는 시험까지 하고, 실제 브라우저 시험과 5.3, 5.4, 5.6의 선행 실험은 컨트롤러가 브랜치를 올려 두 번째 기기에서 돌린 뒤 결과를 구현 에이전트에게 돌려준다. 계획은 작업마다 이 왕복 지점을 넣는다.

## 6. 만드는 쪽에 맡기는 것

- MCP 프로토콜 구현(직접 또는 크레이트), 도구 스키마의 구체적인 꼴, 도구 설명 문구.
- 정책의 저장 형태와 코어 API의 꼴(`session.create` 인자, `session.info`에 정책을 보여 줄지).
- 5.3의 주소 판정, 5.4의 다운로드 귀속, 5.6의 클립보드를 어떤 CDP 기능으로 할지. 각각 작은 실험을 먼저 하고 결과를 문서에 남긴다.
- 작업을 나누는 순서. 단 시험 브라우저 재사용이 첫 작업이다.
