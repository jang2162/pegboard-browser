## 1. 의도

녹화는 **자동차 블랙박스**다(사용자, 2026-11-17). 평소에는 신경 쓰지 않아도 늘 켜져 있고, 오래된 것부터 저절로 지워지고, 무슨 일이 생겼을 때만 꺼내 본다. 보는 사람은 사람이다. 주된 용도는 디버깅이다(사용자 결정, 2026-11-10).

지금(2a까지)은 동작 기록(`actions.jsonl`)만 남는다. 텍스트로는 "클릭이 실패했다"는 알 수 있지만, 그때 화면에 무엇이 떠 있었는지, 명령과 명령 사이에 페이지가 어디로 넘어갔는지, 사람이 무엇을 눌렀는지는 알 수 없다. 2b는 여기에 화면을 붙이고, 사람이 그것을 쉽게 되짚을 재생 화면을 만든다.

## 2. 목표, 하지 않는 것, 실패 조건

**목표**
- 세션을 만들면 설정 없이 화면 녹화가 시작된다.
- 모든 명령의 직전·직후 화면이 남는다(직후는 명령마다 한 장을 찍고, 직전은 그 탭에 마지막으로 저장된 그림이다. 4.2절). 명령 사이의 화면 변화도 남는다.
- `pegboard recording open <id>`로 재생 화면이 열리고, 실패·정책 거부·사람 개입이 시간축에 표시되며, 누르면 그 시점 화면으로 간다.
- 오래된 녹화는 저절로 지워지고, 사람이 표시한 것만 남는다.

**하지 않는 것 (2b 범위 밖)**
- 동영상 내보내기(`recording export --format webm`). ffmpeg가 필요하고, 블랙박스 용도에는 재생 화면으로 충분하다(제안). 필요해지면 따로 넣는다.
- 에이전트에게 화면을 돌려주는 것. 에이전트는 지금처럼 텍스트 동작 기록(`recording show`, `pegboard_recording_get`)만 본다(제안: 보는 사람은 사람).
- 변조 방지(서명, 해시 사슬). 디버깅 용도라 하지 않는다(사용자 결정, 2026-11-10).
- 원격 녹화 열람(5단계), 실시간 화면 보기(5단계).
- 사람의 탭이나 다른 앱의 화면. 세션 탭만 찍는다.

**실패 조건 (동작해도 이렇게 되면 실패)**
- 녹화 때문에 에이전트 명령이 눈에 띄게 느려진다. 기준은 4.6절.
- 사람 프로필의 탭이 한 장이라도 찍힌다.
- 녹화가 디스크를 끝없이 채운다(보존 한도를 넘는다).
- 재생 화면이나 녹화 파일에 에이전트 세션이 닿는다(에이전트가 다른 세션의 화면을 보거나, 재생 서버를 통해 데몬에 닿는다).
- 화면 기록을 끈 도메인의 화면이 남는다. 판정은 탭의 주 프레임 주소로 한다. 다른 페이지 안의 iframe으로 뜬 그 도메인은 찍힌다(계획 사전 검토 C7, 사용자에게 알림).
- 동작 기록에서 가린 값이 재생 화면의 동작 목록(텍스트)에서 드러난다. 화면 프레임은 여기에 들지 않는다(R10): 카드 번호·일회용 코드 입력란의 숫자, 사람이 에이전트 창에서 직접 로그인하는 과정, "비밀번호 보기"를 누른 화면은 그대로 찍힌다. README 알려진 한계에 적는다.

### 접근 방식 (R3)

- **A. 바뀔 때마다 + 동작마다 반드시 (선택).** Chrome의 화면 스트림(`Page.startScreencast`)으로 바뀐 화면을 받되 초당 2장으로 묶고, 명령 앞뒤에 직접 한 장씩(`Page.captureScreenshot`) 찍는다. 명령 사이의 변화와 실패 앞뒤 화면이 모두 남는다. (만든 것은 직후만 찍고, 직전은 그 탭의 마지막 그림을 쓴다: 4.2절)
- **B. 동작마다만.** 가장 가볍지만 명령 사이(자동 이동, 팝업, 사람 개입)가 비어 블랙박스 목적에 어긋난다.
- **C. 일정 간격.** 멈춘 화면이 중복으로 쌓이고 짧은 화면을 놓친다. A, B보다 나은 점이 없다.

## 4. 설계

### 4.1 무엇을 기록하나

| 종류 | 기본 | 비고 |
|---|---|---|
| 동작 기록 | 켜짐 | 이미 있음(`actions.jsonl`). 항목에 직전·직후 프레임 이름(`frameBefore`, `frameAfter`)과 종류(`kind`)를 더했다 |
| 화면 | 켜짐 | 세션 탭마다. 4.2절 |
| 탐색 기록 | 켜짐 | 탭 열림(팝업이면 연 탭), 주 프레임 주소 변화, 닫힘. `navigation.jsonl`. 4.3절 |
| 사람 개입 | 켜짐 | 4.4절 |
| 네트워크 메타데이터 | 꺼짐 | `--record network`. 방법, 주소(`url_for_log`), 상태, 크기, 시간, 오류. **헤더는 아예 기록하지 않는다**(처음 제안은 "세 헤더를 가린다"였다. 쓰지 않으면 메타데이터 범위와 가림이 둘 다 지켜진다). 본문은 기록하지 않는다 |
| 콘솔 | 꺼짐 | `--record console`. 콘솔 메시지와 페이지 오류. 한 줄 1000자. 글 속 http(s)·ws(s)·blob·data 주소는 쿼리, 조각, 계정 정보를 지운다. 그 밖의 글은 페이지가 찍은 그대로다 |

네트워크 본문 기록은 2b에서 만들지 않았다(제안: 민감 정보가 가장 많고 블랙박스 용도에 필수가 아니다). `navigation.jsonl`, `network.jsonl`, `console.jsonl`은 녹화 하나에 파일마다 64 MiB까지이고, 넘으면 `{"ts":…,"capped":true}` 한 줄로 끝난다(화면의 녹화당 한도와 따로 센다).

### 4.2 화면 기록

- **스트림은 녹화기의 자기 CDP 연결에서 건다**(F1 구성 B). 처음 제안은 데몬이 탭마다 유지하는 포커스 유지 세션이었다. 그 세션은 데몬의 주 연결 위에 있어, 프레임이 세션 관리자의 이벤트 처리를 밀어낼 수 있다. 두 구성의 프레임 수와 캡처는 잰 상태에서 같았다(F1). 녹화기 연결은 첫 녹화가 시작될 때 열고, 끊기면 250ms부터 5초까지 늘려 가며 다시 붙고, 녹화 중인 탭에 모두 다시 붙는다. 끊긴 동안은 프레임이 없다.
- 에이전트 쪽 필터는 `Page.startScreencast`, `Page.stopScreencast`, `Page.screencastFrameAck`를 거부한다("pegboard records the session's screen itself"). 0단계 허용목록에는 앞의 둘이 있었고 2b에서 거부 목록으로 옮겼다. agent-browser의 `record`, `stream` 명령은 원래 허용목록 밖이다.
- 스트림 설정은 `{format: jpeg, quality: 60, maxWidth: 1280}`. 프레임은 받자마자 확인(ack)한다(F2). 초당 2장(500ms 간격)을 넘는 프레임은 버리되, 화면이 멈추면 마지막으로 받은 프레임을 남긴다(멈춘 화면이 마지막 상태가 된다).
- 저장: Chrome이 준 JPEG를 그대로 파일로 쓴다. 세션마다 쓰기 스레드 하나가 탭별 파일과 `index.jsonl`을 맡고, 명령은 파일 쓰기를 기다리지 않는다. 쓰기에 실패한 프레임은 버린다.
- **명령의 직후 화면(직후 캡처)**: 명령이 끝나면 그 명령의 탭(agent-browser가 붙어 있는 탭, 없으면 세션의 유일한 탭)을 `Page.captureScreenshot`으로 한 장 찍는다. 품질 60. 배율 1이고 창이 1280 이하면 그대로 찍고, 그렇지 않으면(배율이 1보다 크거나 창이 넓으면) 화면 영역을 `clip`으로 주고 `scale`로 가로 1280에 맞춘다. 배율은 탭에 붙을 때 한 번 읽는다(페이지 확대도 배율에 들어간다).
  - 제한은 명령 하나에 500ms(설계의 최악 1초를 지키려고 정했다. 처음 제안은 캡처 하나에 1초). 넘으면 프레임 없이 명령을 끝낸다. 캡처 자체가 250ms 넘게 걸려 제한에 닿았거나 탭이 준비되지 않은 탭은 **30초 동안(또는 그 탭의 스트림 프레임이 올 때까지) 찍지 않는다**(멈춘 탭이 명령마다 500ms를 먹지 않게).
  - 캡처의 답은 브라우저가 그보다 먼저 보낸 이벤트를 녹화기가 모두 처리한 뒤에 판정한다. 그 사이에 주 프레임이 다른 문서로 넘어갔거나 화면을 끈 주소로 갔으면 버린다.
  - 녹화가 명령을 막거나 실패시키지 않는다. 거부된 명령(argv, 정책, 가드 등 모든 거부 지점)에는 프레임이 없다.
- **명령의 직전 화면**: 캡처하지 않는다(소유자 결정, 2026-11-17, F7). `frameBefore`는 명령이 시작할 때 그 탭에 마지막으로 저장된 프레임이다: 스트림 프레임이나 앞 명령의 직후 캡처. 아직 쓰지 않은 대기 프레임(초당 2장으로 묶느라 잡아 둔 것)은 들지 않으므로 화면보다 최대 약 0.5초 늦을 수 있다. 화면 기록 꺼짐 표시 앞의 프레임, 녹화기 연결이 바뀌기 전의 프레임은 쓰지 않는다. 없으면 비운다.
- `frameBefore`, `frameAfter`가 가리키는 파일은 없을 수 있다(4.5절).
- **찍지 않는 것**: 사람 프로필의 탭(녹화기가 붙기 전에 탭의 컨텍스트를 확인한다), 세션에 속하지 않은 탭, 화면 기록을 끈 도메인의 탭(아래).
- **화면 기록 끄기의 규칙** (F5, `ScreenGate`). 판정은 탭의 주 프레임 주소로만 한다.
  - 들어갈 때: 주 프레임이 끈 주소로 탐색을 시작하면(`Page.frameStartedNavigating`) 바로 닫고, 302처럼 시작 주소로는 모르는 것은 주 프레임 `Page.frameNavigated`에서 닫는다. 닫힐 때 `index.jsonl`에 `off` 표시 한 줄을 쓰고 잡아 둔 프레임을 버린다. 확정되지 않고 멈춘 탐색(`frameStoppedLoading`)은 닫음을 푼다.
  - 나갈 때: 끈 주소(또는 무엇을 보였는지 모르는 상태)에서 다른 주소로 넘어가면, 스트림 프레임은 새 문서(그 `loaderId`)의 `firstContentfulPaint` lifecycle 이벤트까지 버린다. 그 이벤트가 오지 않는 문서(내용을 그리지 않는 페이지)는 다음 탐색까지 기록되지 않는다(닫힌 쪽으로 실패). back/forward 캐시 복원(`frameNavigated.type`이 `BackForwardCacheRestore`, lifecycle 이벤트가 오지 않는다)은 `frameNavigated`부터 250ms 동안 버린다.
  - 직접 캡처는 지금 문서의 `frameNavigated` 뒤에 보낸 것만 쓰고, 위의 기다림(첫 그림, 250ms) 동안에는 찍지 않는다. 그래서 끈 페이지에서 정지한 페이지로 나온 뒤에는 화면이 바뀌거나 첫 그림 뒤의 캡처가 성공할 때까지 `frameBefore`가 없다. F5 판정 줄은 back/forward 캐시 복원 때 캡처 한 장으로 그 구간을 남긴다고 했지만, 만든 것은 그 캡처도 찍지 않는다(닫힌 쪽).
  - **모르면 닫는다**: 녹화기가 탭에 (다시) 붙는 동안은 주소를 알 때까지 닫혀 있다. 처음 보는 탭은, 그 전에 끈 페이지에 있었을 수 있는 흔적(브라우저가 알려 준 주소가 끈 주소이거나 모름, 바로 앞 기록 항목이 끈 주소, 녹화기가 그 탭의 다른 문서를 본 적이 있음, 첫 탭을 제때 따라가지 못함)이 있으면 첫 그림까지 기다리고, 없으면 바로 연다. 세션의 첫 탭은 시작 주소를 열기 전에 녹화기가 미리 붙어 따라간다(500ms 안에 못 붙으면 첫 그림까지 기다린다). 첫 그림 여부는 페이지 스크립트가 흉내 낼 수 없게 격리된 세계에서 `paint` 항목으로 확인한다.
  - 끈 도메인 목록이 비어 있으면 아무것도 기다리지 않는다.
  - 끈 주소 판정: `config.toml`의 `screen_off_domains`의 도메인과 그 하위 도메인. `blob:`, `view-source:`, `filesystem:`은 안의 주소로 판정하고(8겹까지, 더 깊으면 끈 것으로 본다), 목록이 있을 때 호스트 없는 주소(`file:`, `about:srcdoc` 등)는 끈 것으로 본다. `data:`와 `about:blank`는 찍는다.
- **가려진 탭** (F4): 보이는 탭, 같은 창의 뒤쪽 탭, 최소화한 창, 다른 창에 가려진 창에서는 스트림과 직접 캡처가 모두 왔다(뒤쪽 탭과 최소화는 초당 약 4장). 다른 Space, 화면 잠금, 디스플레이 절전은 재지 않았다(수동 확인 P3, P4). 프레임이 없는 구간은 재생 화면에 "화면 없음"으로 보인다.
- **녹화 하나의 한도**: 화면 바이트가 `max_per_recording_gb`(기본 1 GB)에 닿으면 모든 탭의 `index.jsonl`에 `capped` 표시를 한 번 쓰고 그 녹화의 화면 기록만 멈춘다. 동작 기록과 탐색 기록은 계속한다.

### 4.3 탐색 기록

녹화기의 자기 세션에서 본 세션 탭의 이벤트로 `navigation.jsonl`에 `{ts, targetId, event, url, opener}`를 남긴다. `event`는 `created`(세션 탭이 생김. 팝업이면 `opener`), `navigated`(주 프레임 `frameNavigated`), `closed`(세션 범위를 떠남). 녹화기가 붙을 때 이미 다른 페이지에 있던 탭은 그 페이지를 한 번 `navigated`로 적는다. 주소는 동작 기록과 같은 규칙(`url_for_log`: 쿼리, 조각, 계정 정보 제거)으로 줄인다. 같은 문서 안의 이동(`pushState`, `#` 이동)은 적지 않는다.

### 4.4 사람 개입

블랙박스에서 가장 중요한 "사고" 중 하나다. 측정(F6) 결과 탐색 이벤트에도 확장 신호에도 사람과 에이전트(또는 페이지 스크립트)를 확실히 가르는 신호가 없었다. 그래서 **시간으로만 가리고, 모든 표시는 "사람 개입 가능성"(`certain: false`)이다.** 페이지에 입력 감지 스크립트를 넣는 방법은 쓰지 않았다.

- 명령 구간: 세션의 명령이 모든 거부 지점을 지난 뒤 실행되기 시작할 때부터 끝날 때까지, 그리고 끝난 뒤 1초(유예). `session create`도 명령으로 센다. 같은 프로필의 다른 세션이 명령 구간에 있을 때의 탭 전환도 명령의 것으로 본다(탭 전환은 어느 세션 것인지 가를 수 없다).
- 표시하는 것: 명령 구간 밖에서 세션 탭의 주 프레임이 다른 문서로 넘어간 것(주소창 입력, 뒤로·앞으로, 링크 클릭, 폼 제출. 링크·폼이면 "followed a link or form outside a command", 그 밖은 "navigated outside a command: <주소>"), 세션 탭이 앞 탭이 된 것("switched to this tab").
- 표시하지 않는 것: `frameRequestedNavigation`의 이유가 `scriptInitiated`, `metaTagRefresh`, `httpHeaderRefresh`, `reload`, `initialFrameNavigation`인 탐색, 같은 문서 안의 이동, 탭의 첫 페이지(탭이 열린 것으로 본다), 요청 가드가 스스로 다시 불러온 것과 pegboard가 다운로드 정책을 걸려고 앞으로 가져온 탭(pegboard가 미리 알린 것, 5초 안), 브리지가 탭을 닫은 뒤 2초 안의 탭 전환(Chrome이 옆 탭을 앞으로 가져온다).
- 사람과 같이 표시되는 것: 스크립트의 `history.back()`·`a.click()`, 페이지가 연 팝업이 닫힐 때 돌아오는 탭 전환, 명령이 끝나고 1초 넘게 지나 끝난 느린 탐색.
- 탭 전환은 CDP로 보이지 않아 브리지 확장의 서비스 워커가 `chrome.tabs.onActivated`를 바인딩으로 알려 준다. 워커가 다시 뜨면 데몬이 다시 붙고 바인딩을 다시 걸어, 워커가 모아 둔 전환(최근 50개, 60초 안의 것)을 넘겨받는다(단위 시험으로만 확인). **H9**: 실제 브라우저에서 브리지 워커가 저절로 멈추는 것은 본 적이 없고, 강제로 멈춘 워커는 어떤 방법으로도 다시 뜨지 않았다. 그래서 브리지 호출은 먼저 워커에 2초 핑을 보내고, 답이 없으면 떠 있는 워커를 한 번 찾아 붙고, 없으면 곧바로 `bridge_asleep`으로 실패한다(깨우지 않는다. 30초 기다리지 않는다). 그때 새 탭, 세션 만들기와 닫기는 브라우저를 다시 시작할 때까지 실패하고, 있는 탭의 명령은 된다.
- 기록: `actions.jsonl`에 `{"kind":"human", ts, targetId, url, what, certain}` 항목. `seq`는 쓴 순서, `ts`는 일이 일어난 때다(늦게 전해진 탭 전환은 나중 명령보다 큰 `seq`에 이른 `ts`). 읽는 쪽(재생 화면 포함)은 `ts`로 정렬한다.

### 4.5 저장 형식

architecture.md 8절의 구조를 따른다. 형식 버전 2(`manifest.json`의 `format`). 형식 1(2b 이전) 녹화도 그대로 읽는다.

```
<PEGBOARD_HOME>/recordings/<recordingId>/
  manifest.json        + keep(bool), screen("none"|"recorded"|"capped"|"pruned"), record(["network","console"]), sizes
  actions.jsonl        + kind("command"|"human"), frameBefore, frameAfter, what, certain
  navigation.jsonl
  screen/<targetId>/index.jsonl, 000001.jpg ...
  network.jsonl        --record network 일 때만
  console.jsonl        --record console 일 때만
```

- `screen`은 처음 제안의 bool 대신 넷이다("화면 지워짐", "화면 기록 멈춤"을 보이려고). `sizes`는 녹화가 끝날 때 잰 바이트(전체, 화면).
- 프레임 이름은 `screen/` 기준 `<targetId>/<file>`이다(예: `9A1F…/000031.jpg`. 처음 예시의 `"000031.jpg"`는 탭이 여럿일 때 모호하다). 타깃 ID는 32자 대문자 16진수, 파일은 숫자 6~10자리 `.jpg`. 쓰는 쪽과 읽는 쪽이 모두 이 꼴만 받는다.
- `index.jsonl` 한 줄은 프레임이면 `{ts, file, url, width, height, kind}`(`kind`는 `change` 또는 `after`), 표시면 `{ts, kind: "off"|"capped", url?}`이다. `ts`는 프레임을 받은 시각이다(프레임의 자체 시각은 이벤트와 순서가 어긋날 수 있었다: S6b).
- 동작 기록의 `frameBefore`, `frameAfter`는 그 파일이 끝내 생기지 않은 프레임을 가리킬 수 있다: 디스크에 쓰지 못했을 때, 그 캡처가 녹화 하나의 한도를 넘겼을 때, 세션이 끝날 때 writer가 제한(5초) 안에 끝내지 못했을 때(명령은 파일 쓰기를 기다리지 않는다, 4.6절). 보존 정리로 화면이 지워진 녹화도 같다. 읽는 쪽(보존, 재생 화면)은 없는 파일을 "화면 없음"으로 다룬다.
- 디렉터리 권한은 소유자 전용(0700, 파일 0600). 파일은 새로 만들 때만 쓰고(이미 있으면 거부) 링크는 따라가지 않는다.

### 4.6 성능 기준

- 명령 하나에 녹화가 더하는 시간: 중앙값 **60ms 이하**(소유자 결정 2026-11-18, 처음 제안은 50ms), 최악 **1초**.
- 측정: 녹화를 켜고 끈 상태로 1단계 호환 표의 명령들을 돌려 비교했다. 시험은 `e2e_recording`의 `recording_overhead_meets_the_targets`(명령마다 중앙값 60ms 이하, 최대 1초 이하를 확인한다).
- 측정 결과(작업 1, 녹화기 흉내, 배율 1 화면): 명령 앞뒤 캡처로는 14개 명령 중 12개가 중앙값 50ms를 넘었고, 직후 캡처만 하면 세 번 모두 지켰다(명령별 중앙값 20~48ms, 최대 90ms. 여유는 가장 좁을 때 2ms). 그래서 직전 캡처를 뺐다(소유자 결정, 2026-11-17): `frameBefore`는 그 탭에 마지막으로 저장된 프레임이다. 직후 캡처의 제한은 500ms이고, 제한을 넘긴 탭은 30초 동안(또는 스트림 프레임이 올 때까지) 찍지 않는다. 자세한 것은 spike-findings.md "2b단계 측정"의 S2, F7.
- 측정 결과(작업 4, 실제 녹화기, 2026-11-17, 두 번째 기계: 데스크톱 Mac, 화면 배율 1, 명령마다 20쌍): `e2e_recording`의 `recording_overhead_meets_the_targets`. 배포용 빌드와 디버그 빌드의 더해진 시간 중앙값(ms):

| 명령 | 더해진 시간 중앙값, 배포용 빌드 (ms) | 더해진 시간 중앙값, 디버그 빌드 (ms) |
|---|---|---|
| `open` | 44 | 40 |
| `snapshot -i` | 26 | 26 |
| `click` | 48 | 49 |
| `fill` | 51 | 48 |
| `type` | 51 | 54 |
| `press Enter` | 32 | 32 |
| `get url` | 36 | 34 |
| `get text` | 37 | 34 |
| `eval` | 32 | 34 |
| `scroll down 200` | 30 | 32 |
| `wait 100` | 31 | 29 |
| `screenshot` | 40 | 34 |
| `tab new` | 41 | 40 |
| `tab list` | 33 | 28 |
| 최대 (모든 명령) | 87 | 88 |

  Chrome의 직접 캡처가 명령마다 16~41ms(중앙값)를 차지하고, 파일 쓰기는 명령을 기다리게 하지 않는다(writer에 넘기는 데 0.1ms 이하). 50ms를 넘은 것은 `fill`, `type`(51~54ms)이었고, 화질과 크기를 낮춰도 캡처 시간은 거의 줄지 않으므로(작업 1 S2) 소유자가 기준을 60ms로 올렸다(2026-11-18). 자세한 것은 spike-findings.md "2b단계 측정"의 "작업 4".

- 위 표는 12d2703에서 쟀다. 그 뒤 캡처를 이벤트 순서대로 판정하는 기다림(cd48c39)과 넓은 창의 `clip`(배율 1이어도 창이 1280보다 넓으면)을 더했고, dff5bac에서 다시 잰 배포용 빌드의 더해진 시간 중앙값은 명령마다 26~47ms, 전체 최대 73ms였다(4672338에서도 중앙값 26~47ms). 명령별 최대는 남기지 않았다(전체 최대만 있다).
- 재지 않은 것: 레티나 화면(배율 2)의 캡처 시간과 크기, 1280보다 넓은 창에서 `clip`을 쓰는 캡처의 시간(작업 1 V3는 배율 1, 1280 창에서 `clip`이 15ms 느렸다). 수동 확인 P7.

### 4.7 보존

- 데몬이 시작할 때(먼저 앞선 데몬이 끝을 적지 못한 녹화에 마지막으로 파일을 쓴 시각을 끝으로 적고), 1시간마다, 그리고 세션이 끝날 때마다 정리한다. `recording prune [--dry-run]`으로 지금 정리할 수 있다.
- 지우는 순서: 끝난 지 `max_age_days`(기본 14일)가 지난 것은 통째로. 그다음 전체가 `max_total_gb`(기본 5 GB)를 넘으면 끝난 녹화 중 끝난 시각이 오래된 것부터 **화면(`screen/`)만** 지운다(제안). 동작 기록, 탐색 기록, 선택 기록은 크기 때문에 지우지 않고 14일까지 둔다(작고, 에이전트가 `pegboard_recording_get`으로 되읽는다). 화면이 지워진 녹화는 `screen: "pruned"`이고 `recording list`에 "screen pruned", 재생 화면에 "화면 지워짐"으로 보인다.
- 진행 중인 녹화는 지우지 않지만 전체 크기에는 센다. `keep`한 것은 지우지도 세지도 않는다. 쌓이면 사람이 지운다(`recording delete`, 진행 중이면 `recording_running`). `recording list`에 전체 용량과 `keep` 용량을 보여 준다(`--json`의 `totalBytes`, `keptBytes`는 거르지 않은 전체).
- 2b 이전에 만들어진 녹화(형식 1, 동작 기록만)도 같은 14일 규칙을 따른다(사용자 결정 R4가 녹화 전체에 대한 것이므로). **2b를 처음 켜는 날, 끝난 지 14일이 지난 기존 동작 기록이 지워진다.** README에 적었다.
- 진행 중인 녹화 하나의 화면이 `max_per_recording_gb`(기본 1 GB)에 닿으면 그 녹화의 화면 기록만 멈추고 동작 기록은 계속한다(4.2절, 재생 화면에 "화면 기록 멈춤(녹화 하나 1GB)").
- 녹화를 통째로 지울 때는 잠금 안에서 `recordings/.deleting-<id>-…`로 이름을 바꾸고 잠금 밖에서 지운다. 지우다 끊기면 그 디렉터리만 남고 다음 정리(데몬 시작 포함)가 지운다. `manifest.json`을 읽을 수 없는 녹화 디렉터리는 건드리지 않고 `daemon.log`에 (데몬마다 한 번) 남긴다. `recordings/` 바로 아래의 녹화 ID 꼴의 진짜 디렉터리만 읽고 지운다(링크는 따라가지 않는다).
- 설정: `<PEGBOARD_HOME>/config.toml`의 `[recording]` `max_age_days`(1~3650), `max_total_gb`, `max_per_recording_gb`(GB는 10^9바이트, 0.001 이상), `screen_off_domains`(호스트 이름이나 IP 목록. 소문자로 맞추고 중복을 없앤다. 한글 도메인은 `xn--` 꼴로). 설정 파일이 없으면 기본값. 데몬이 시작할 때 한 번 읽으므로 바꾸면 데몬을 다시 띄운다. 잘못 쓰면 `pegboard browser start`가 `invalid_params`(종료 코드 2)로 끝나고 데몬이 뜨지 않는다.

### 4.8 재생 화면

- `pegboard recording open <id>`: 데몬이 녹화를 확인하고 일회용 주소 `http://127.0.0.1:<포트>/r/<토큰>/`를 준다. **CLI가** 그 주소가 이 꼴인지 확인한 뒤 `/usr/bin/open`으로 사람의 기본 브라우저에서 연다(사람의 프로세스가 사람의 브라우저를 연다. 에이전트 프로필 창에서 열지 않는다). 열지 못하면 주소를 찍고 종료 코드 1.
- 재생 서버는 데몬이 시작할 때 루프백의 임시 포트 하나에 뜬다. 토큰은 32바이트 난수(base32 52자)이고 열 때마다 새로 만들며 그 녹화 하나에만 유효하다. 30분 뒤(단조 시계와 벽시계 중 먼저 닿는 쪽), 또는 데몬이 끝날 때 사라진다. 지워진 녹화는 링크가 남아 있어도 열리지 않는다.
- 서버는 `GET`과 `HEAD`만, `Host`가 정확히 `127.0.0.1:<포트>`인 요청만 받는다. 그 녹화의 `screen/<타깃>/<파일>`만 내주고(링크, 디렉터리 밖, 32 MB 넘는 파일 거부), 모르는 토큰과 없는 것은 같은 404다. 모든 응답에 `default-src 'none'` CSP, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`. 연결 하나에 요청 하나, 동시에 32개, 연결마다 30초.
- 이 포트는 2a 주소 규칙의 "pegboard 자신의 포트"에 들어가 에이전트 세션에서는 어떤 정책으로도 닿지 않는다.
- **판정은 서버가 한다**: 페이지는 `data` 하나를 받아 그린다. 서버가 동작마다 탭별로 직전·직후에 보일 것(프레임, 화면 기록 꺼짐, 화면 기록 멈춤, 화면 지워짐, 화면 없음)을 정해 보낸다. 그 동작 자신의 탭은 `frameBefore`/`frameAfter`(파일이 있을 때만)를, 다른 탭과 프레임 이름이 없는 동작(사람 개입, 거부된 명령)은 그 시각(직전) 또는 다음 동작의 시각(직후, 마지막 동작이면 녹화의 끝)에 그 탭에 마지막으로 남은 것을 쓴다. 그 사이에 그 탭이 다른 주소로 넘어갔으면 "화면 없음"이다. 페이지의 스크립트에는 시간 비교가 없다.
- 화면 구성 (사용자 확인, 2026-11-17):

```
┌ 세션 "조사" · 14:02–14:19 · 명령 42 · 실패 2 · 거부 1 ┐
│  ┌──── 화면 (그 시점의 탭) ────┐    동작 목록          │
│  │                             │    14:05 open         │
│  │                             │  ▶ 14:06 click ✗      │
│  │                             │    14:06 fill 🔒      │
│  └─────────────────────────────┘    14:07 거부 ⛔       │
│  [탭: example.com | 팝업]  ◀ 직전  직후 ▶   14:09 사람 개입 │
│  ──●────✗──⛔────●──────────●── 시간축 ───────────────  │
└──────────────────────────────────────────────────────┘
```

  - 머리글: 세션 이름, 시작–끝(진행 중), 명령, 실패, 거부, 사람 개입 수, 화면 상태, 녹화 ID. "거부"는 `policy_denied`와 `argv_rejected`, "실패"는 그 밖의 실패한 명령이다.
  - 열면 시간 순서로 첫 사고(실패, 거부, 사람 개입) 위치의 직전 화면에서 시작한다. 사고가 없으면 처음부터.
  - 시간축의 사고 표시(✗ ⛔ 👤)를 누르면 그 동작의 직전 화면, 같은 표시를 한 번 더 누르면 직후 화면.
  - 왼쪽·오른쪽 화살표 키: 앞·다음 동작.
  - 탭이 여럿이면 화면 아래의 탭 단추(그 탭의 마지막 주소의 호스트)로 고른다.
  - "네트워크 · 콘솔" 칸: 앞 동작부터 그 동작의 직후까지의 선택 기록 줄.
  - 동작 목록의 값은 동작 기록 그대로(가린 값은 가린 채, 가린 항목 끝에 🔒) 보인다.
  - 페이지에서 온 글(세션 이름, 주소, 오류 문구, 사람 개입의 `what`)은 `textContent`로만 넣는다(HTML로 해석하지 않는다).
  - 링크가 끝났거나 녹화가 지워져 그림이 안 열리면 "녹화를 열 수 없습니다" 안내를 보인다.
- 외부 자원(스크립트, 글꼴)을 쓰지 않는다. 바이너리에 넣은 HTML, JS, CSS 하나씩.

### 4.9 명령

| CLI | MCP | 설명 |
|---|---|---|
| `recording list [--session S] [--failed] [--kept]` | `pegboard_recording_list` (기존) | 목록에 끝/진행 중, 크기, 화면 상태, keep, 실패·거부 수를 더했다. 전체 용량 줄은 CLI와 MCP 운영자 모드에만 |
| `recording show <id>` | `pegboard_recording_get` (기존) | 텍스트. 사람 개입 항목도 나온다(`human: <what> (possibly)`). 프레임은 이름만 |
| `recording open <id>` | 없음(어느 모드에도) | 재생 화면 |
| `recording keep <id>` / `unkeep <id>` | `pegboard_recording_keep {recordingId, keep}`, 운영자 모드만 | 보존 표시 |
| `recording delete <id>` | `pegboard_recording_delete {recordingId}`, 운영자 모드만 | 진행 중이면 `recording_running` |
| `recording prune [--dry-run]` | 없음 | 지금 정리 |
| `session create --record network,console` | 운영자 모드의 `policy.record` / `pegboard mcp --record ...` | 선택 기록 켜기. 기본 모드의 도구로는 켤 수 없다 |

코어 API: `recording.list`, `recording.get`, `recording.open`, `recording.keep`, `recording.delete`, `recording.prune`. 2a의 기록 조회처럼 토큰이 필요 없다(소켓 소유자 검사만). MCP 기본 모드의 에이전트는 자기 녹화의 텍스트만 읽는다(2a와 같다). keep/delete는 사람의 일이라 기본 모드에 없다(목록에도 없고, 부르면 없는 도구와 같은 오류).

## 5. 위험과 측정할 것

첫 작업(작업 1)에서 잰 결과와 남은 것. 자세한 것은 spike-findings.md "2b단계 측정".

1. 가려진 탭·최소화된 창에서는 스트림 프레임과 직접 캡처가 모두 왔다(F4). **다른 Space, 화면 잠금, 디스플레이 절전은 재지 못했다**(수동 확인 P3, P4).
2. 명령 앞뒤 캡처로는 50ms를 못 지켜 직전 캡처를 뺐고, 기준을 60ms로 올렸다(4.6절, F7).
3. 사람 개입을 확실히 가르는 신호는 없었다(F6). 모두 "가능성"이다. 사람이 직접 한 입력은 재지 못했다(합성 운영체제 입력만. 수동 확인 P5).
4. 2a 방어(클립보드, 주소 규칙, 다운로드, 대화 상자, 팝업)는 녹화기 옆에서 그대로였다(M3 해당 없음). 에이전트는 화면 스트림을 시작·중지할 수 없다.
5. 30분 197MB(배율 1, 화면이 계속 바뀌고 명령 앞뒤 캡처를 넣은 상한, F8). 5 GB에 화면 약 12.7시간 분량이라 화면을 보존하는 기간은 사실상 용량 한도가 정한다.
6. 재지 못한 것: 레티나 화면(배율 2)의 캡처 시간·크기·디스크 사용량, 무거운 페이지와 실제 사이트에서의 F5 규칙(back/forward 캐시 250ms가 충분한지), 실제 브라우저에서 브리지 워커가 다시 뜨는 경로(H9).

## 6. 만드는 쪽에 맡긴 것과 정한 값

- JPEG: Chrome이 준 것을 그대로 저장한다. 프레임 하나에 파일 하나.
- 재생 화면의 세부 모양: 4.8절. 키보드는 좌우 화살표.
- 정리 주기: 데몬 시작, 1시간마다, 세션이 끝날 때.
- 제안 숫자 가운데 바꾼 것: 직전 캡처 없음(직후만), 캡처 제한 명령 하나에 500ms(처음 1초), 멈춘 탭 30초 건너뛰기, 성능 기준 중앙값 60ms(처음 50ms), 사람 개입은 모두 "가능성"과 명령 구간 + 1초 유예. 그대로인 것: 품질 60, 가로 최대 1280, 초당 2장, 14일, 5 GB, 녹화 하나 1 GB, 링크 30분.
