## Findings and decisions
1. universal-access isolated world: no allowed command lets a caller run its own script in an isolated world (eval and wait --fn use Runtime.evaluate in the main world; `eval_runs_in_the_main_world_and_a11y_works` shows a value set by one eval is visible to the next and `a11y` still works; `a11y` runs a fixed script). So the test is at proxy level. Through the session proxy a `grantUniveralAccess:true` world could NOT fetch/XHR file://, chrome://, chrome-extension://, filesystem:, and sees only the agent profile's cookie/localStorage (the human tab holds spike=1 on the same origin). Measured on Chrome 157: the flag grants no cross-origin network access to fetch or XHR at all (printed in the test output, not asserted). Therefore the proxy filter was NOT changed (flag is still passed through).
2. `session list` is a pegboard command, not forwarded, even with `--session` (exit 0, ids and names, no tokens). My earlier manual "exit 2" was a zsh word-splitting mistake. The brief's `session list` => exit 2 case does not hold: the real behaviour is exit 0. The test asserts instead that its output contains no token (README already lists it as a no-token command). The other brief cases (`close`, `stream enable`, `connect`, etc.) really exit 2 and are asserted so. `--auto-connect snapshot` as first word fails in clap (exit 2).
3. `fill #name -- --cdp <port>` is accepted by design (literal text after `--`); the test proves the text is typed into the field and not read as a flag, instead of listing it as refused.
4. `session info <id>` / `session close <id>` with a missing token return exit 1 session_not_found (the daemon refuses), not exit 2; only `--session <id>` (commands) is a client-side usage error (code: "A wrong or missing token is for the daemon to refuse"). Deviates from the task note; the test asserts the real behaviour and also that all sessions survive.
5. `Target.createTarget` without a context from the human side lands in the agent profile's context (the browser uses the last active window's profile). The Human helper therefore opens its second tab with `window.open` + userGesture from the human page, as e2e_proxy does.
6. Flaky pre-existing test: `stale_socket_is_removed_only_when_lock_is_free` (e2e_cli) failed in 2 of 4 default `cargo test --workspace` runs (a forking parallel test inherits the lock fd; the test already loops 2 s). Not touched.

## agent_does_not_steal_focus: what it proves
Asserts that the human window's tabs keep the same `document.visibilityState` (which tab is active) before and after the agent opens, clicks, fills, creates tabs, and that the human profile still has the same number of tabs. It does not prove OS focus: `document.hasFocus()` was false in my runs because other apps had focus, so it is printed, not asserted. If another app covers the Chrome window the whole time, every human tab reads "hidden" before and after and the assertion holds trivially. In my runs the active tab read "visible" before and after.

## FINDING (not fixed, src out of scope): the proxy's single `Target.closeTarget` is unreliable
In `finish_tab`'s refusal branch the stray tab was NOT closed in ~4 of 10 runs. Reproduced with no proxy involved (scratch test, deleted): `bridge.create_tab(group,url)` then immediately `Target.getTargetInfo` + `Target.closeTarget` on the browser connection: reply `{success:true}` yet the tab stays in 3 of 8 iterations; a second `Target.closeTarget` a moment later closes it. (`bridge.close_targets` on such a tab errors "unknown target".) So Chrome ignores a closeTarget sent right after creation; the proxy sends it once and ignores the reply. In the real failure case that branch guards (bridge puts a tab in the wrong, e.g. human, profile) the tab could be left open. Suggested fix for the controller to decide: retry/verify closeTarget in `finish_tab` (e.g. re-send after a short delay until the target is gone). The new test therefore asserts the refusal and scope hard, and treats the closure as a printed `KNOWN GAP` (and closes the stray itself).
