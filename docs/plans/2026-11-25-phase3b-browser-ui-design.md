## 1. 의도

3a로 Pegboard.app은 데몬을 띄우고 파이프로 CDP를 넘기는 브라우저가 됐다. 그러나 사람이 매일 쓰는 브라우저로 두기에는 화면이 아직 Chromium이다. 에이전트 창과 사람 창이 똑같이 생겼고, 2a에서 "확인이 필요한 동작"으로 정해 두었던 업로드와 쿠키·저장소 쓰기는 실시간으로 물을 곳이 없어 거부로 바꿔 두었다(2a D5). 구글 로그인 버튼과 내장 비밀번호 관리자가 그대로 있고, 메뉴와 설정 화면은 "Chromium"이라고 말하며, 아이콘은 임시다.

3b는 이것을 고친다. 가장 큰 일은 **확인 창**이다: 에이전트가 `upload`나 `state` 명령을 보내면 데몬이 명령을 멈추고, 브라우저가 그 세션의 에이전트 창에 브라우저 자체의 대화상자를 띄워 사람에게 묻고, 사람이 고른 답(또는 60초 뒤 거부)으로 명령이 이어지거나 끝난다. 나머지는 작은 패치들이다: 에이전트 창 표시, 에이전트 프로필 숨기기, 구글 로그인·비밀번호 관리자 끄기, 문자열과 아이콘, 데몬 다시 띄우기를 포기했을 때의 알림.

## 2. 목표, 하지 않는 것, 실패 조건

**목표**
- `upload`와 `state`의 기본이 "거부"에서 **"묻기"**로 바뀐다. 포크 모드에서 묻기는 그 세션의 에이전트 창에 뜨는 확인 창이고, 답은 허용 / 거부 / 이 세션에서 계속 허용, 60초 동안 답이 없으면 거부다.
- 코어 API에 예약해 둔 `confirm.respond`와 알림 `confirm.required`가 동작한다. 브라우저의 확인 창은 응답자 중 하나이고, 브라우저가 아닌 클라이언트도 답할 수 있다.
- 확인의 결과(허용·거부·시간 초과, 누가)가 동작 기록에 남고, CLI·MCP 결과가 "사람이 거부"와 "시간 초과"를 구분한다.
- 에이전트 창이 사람 창과 한눈에 구분된다.
- 에이전트 프로필이 프로필 메뉴와 프로필 선택 화면에 보이지 않고, 그 때문에 시작할 때 선택 화면이 뜨지 않는다.
- 구글 로그인 UI가 보이지 않고, 내장 비밀번호 관리자가 저장을 제안하지 않는다(사람은 Bitwarden 같은 확장을 쓴다. 2026-11-10 결정).
- About 화면, 메뉴, 설정 화면의 제품 이름이 Pegboard이고, 임시가 아닌 앱 아이콘이 있다.
- 데몬 다시 띄우기를 포기하면(F8: 1분에 4번째) 사람이 보는 알림이 뜬다.

**하지 않는 것 (3b 범위 밖)**
- `network` 분류의 확인(아래 B3). `network route|har`는 문법에 없고 이번에도 넣지 않는다.
- 키체인 `Pegboard Safe Storage` 확인 창 대응, 서명·공증, 제대로 서명한 빌드의 `AperitifHelpers` 확인, pegboard 홈과 브라우저 사용자 데이터 디렉터리 나누기(3c).
- 확인 창의 번역. 3b의 확인 창과 알림 문구는 한국어 하나다(B14).
- 순정 Chrome 모드의 화면. 순정 모드는 개발·시험용이고 확인 창이 없다(B5).

**실패 조건 (동작해도 이렇게 되면 실패)**
- 페이지나 에이전트가 확인에 답하거나 확인을 꾸밀 수 있다: 에이전트의 CDP 입력, `dialog accept`(`Page.handleJavaScriptDialog`), 세션 프록시를 거친 `Pegboard.*`, MCP 도구 어느 것으로도 확인이 풀리면 안 된다.
- 세션 A에 대한 답이 세션 B의 명령을 풀거나, "이 세션에서 계속 허용"이 다른 세션이나 다른 분류를 넓힌다.
- 확인 창이 보여 준 것과 실제로 일어난 일이 다르다(승인 뒤 파일이 바뀌었는데 바뀐 파일이 올라간다, 승인 뒤 페이지가 다른 출처로 갔는데 그 출처에 쓴다).
- 확인을 기다리는 명령이 끝나지 않는다: 시간 초과, 세션 닫기, 데몬 종료, 브라우저 쪽 응답자가 사라짐 어느 경우에도 명령은 정해진 시간 안에 끝난다.
- 확인 창이 사람이 쓰던 창의 키보드 초점을 가져간다.
- 사람 프로필에 에이전트 표시(테마, 창 제목)나 프로필 숨기기가 걸린다.
- 1~2단계와 3a의 보장이 약해진다(3a 계획 Global Constraints의 목록 그대로).

### 접근 방식 (B4, B8)

- **A. 데몬이 중개하고, 브라우저는 창만 (선택).** 판정과 대기와 시간은 모두 데몬의 확인 중개자(`confirm.rs`)가 쥔다. 브라우저는 `Pegboard.requestConfirmation`으로 창을 띄우고 답을 이벤트로 돌려줄 뿐이다. API 응답자와 브라우저 응답자가 같은 표를 본다. 시계가 하나라 시간 초과가 하나로 정해진다.
- **B. 브라우저가 판정까지.** CDP 요청 하나를 60초 붙들고 답을 응답으로 돌려준다. 데몬의 CDP 요청 제한(30초)과 부딪히고, API 응답자와 경쟁을 브라우저와 데몬 두 곳에서 풀어야 한다. 버렸다.
- **C. 웹 페이지로 된 확인 창.** 사람 프로필이나 에이전트 프로필의 탭에 확인 페이지를 연다. 에이전트가 그 탭에 닿을 수 있고(에이전트 프로필), 페이지가 흉내 낼 수 있어 실패 조건 첫 줄을 지키기 어렵다. 버렸다.

## 4. 설계

### 4.1 정책: 묻기

지금 `policy::judge_action`은 허용 아니면 거부다. 기본 분류표에 셋째 값을 둔다.

| 분류 | 기본 | `--allow` | `--deny` |
|---|---|---|---|
| `navigate` … `interact`, `eval`, `download` | 허용 | 효과 없음(지금처럼 `invalid_params`) | 거부 |
| `upload` | **묻기** | 묻지 않고 허용(`--upload-dir` 필요) | 묻지 않고 거부 |
| `state` | **묻기** | 묻지 않고 허용 | 묻지 않고 거부 |
| `clipboard` | 거부 | 허용(프로필 단위) | 효과 없음(`invalid_params`) |

- `--deny upload`, `--deny state`는 지금 "효과 없음"으로 거부되던 것이 이제 뜻을 갖는다. `--upload-dir`만 있고 `--allow upload`가 없는 정책도 이제 맞다(묻기 + 폴더 제한).
- 판정 결과는 `Verdict::{Allow, Ask, Deny(RpcError)}`. `Ask`는 세션이 그 분류를 "이 세션에서 계속 허용"으로 받았으면 `Allow`가 된다. 그 받은 목록은 세션의 실행 중 상태이고 정책(`SessionPolicy`, 만들 때 고정)은 바뀌지 않는다. `session info`는 둘을 따로 보여 준다(`allowedForSession`).
- 받은 목록은 프로필 고정(D8)과 상관없다. `state`와 `upload`는 프로필 단위 항목이 아니다.
- MCP 기본 모드의 에이전트는 어떤 도구로도 받은 목록을 바꿀 수 없다. 받은 목록을 바꾸는 길은 확인에 대한 답 하나뿐이다.

### 4.2 확인 중개자 (`confirm.rs`)

데몬 안에 하나. 대기 중인 확인의 표를 쥔다.

- **확인 하나** = `confirmId`(32자리 소문자 16진수, 128비트 난수) → {세션 ID, 분류, 보여 줄 내용, "이 세션에서 계속 허용"을 내놓을지, 만든 시각, 답을 보낼 곳}. 세션마다 동시에 하나(세션의 명령은 한 번에 하나다: `service.rs` `begin_command`).
- **응답자**: 브라우저(포크 모드에서 `Pegboard` 도메인을 쥔 데몬의 제어 연결)와 API 구독자(`confirm.subscribe` 연결). 확인을 만들 때 응답자가 하나도 없으면 바로 `no_responder`로 거부한다(B5). 브라우저 응답자는 창을 띄우지 못하면(그 프로필에 창이 없음, 도메인 오류) 응답자에서 빠진다. 남은 응답자가 없으면 그 자리에서 `no_responder`.
- **경쟁**: 표의 자물쇠 안에서 처음 도착한 답이 확인을 끝낸다. 늦은 답은 `confirm_not_found`를 받는다. 끝나면 중개자는 브라우저 창을 닫게 하고(`Pegboard.cancelConfirmation`) 구독자에게 `confirm.resolved`를 보낸다.
- **세션 묶기**: 답은 `confirmId` 하나만 끝낸다. "이 세션에서 계속 허용"은 그 확인의 세션 ID의 받은 목록에 그 확인의 분류 하나를 더한다. 다른 세션 ID나 다른 분류를 실어 보낼 자리가 답의 모양에 없다.
- **끝나는 길**(어느 것이든 명령은 끝난다): 답(허용, 이 세션에서 계속 허용, 거부), 60초(`CONFIRM_TIMEOUT`, `timed_out`), 세션 닫기(`cancelled`. 닫기는 세션의 기록 자물쇠를 잡기 **전에** 그 세션의 확인을 취소한다. 기다리는 명령이 그 자물쇠를 쥐고 있기 때문이다), 데몬 종료(`cancelled`), 응답자가 모두 사라짐(`no_responder`: 브라우저 제어 연결이 끊기고 구독자도 없다).
- 시간 제한은 명령의 `timeoutMs`와 따로 센다. 확인 대기는 명령 실행 시간에 들지 않는다. 그래서 CLI·MCP의 소켓 읽기 제한(`api::Client`, 지금 `timeoutMs + 15초`)에 `CONFIRM_TIMEOUT`을 더한다.
- 쉬는 세션 닫기(1시간)는 기다리는 동안 세지 않는다(지금도 명령이 도는 동안은 세지 않는다).

**API** (코어 API, 소유자 전용 소켓):

| 메서드·알림 | 내용 |
|---|---|
| `confirm.subscribe` → `{}` | 이 연결을 알림 통로로 바꾼다. 그 뒤 서버가 한 줄에 하나씩 알림을 보낸다. 쉬는 연결 끊기(10초)가 걸리지 않는다. 연결이 끊기면 구독이 끝난다 |
| 알림 `confirm.required` | `{confirmId, sessionId, sessionName, profile, class, details:[{label, value}], offerAllowForSession, expiresAt}` |
| 알림 `confirm.resolved` | `{confirmId, outcome, by}` |
| `confirm.list` → `{pending:[confirm.required의 params]}` | 지금 기다리는 확인 |
| `confirm.respond {confirmId, answer}` → `{}` | `answer` = `approve` \| `deny` \| `allowForSession`. 없는 ID나 끝난 확인은 `confirm_not_found`. `allowForSession`을 내놓지 않은 확인에 그 답은 `invalid_params` |

- 이 소켓에 닿는 같은 사용자의 프로세스는 답할 수 있다. 지금도 그런 프로세스는 `session.create`로 더 넓은 정책의 세션을 만들 수 있으므로 더 넓어지는 것이 없다(architecture.md 11절 "남는 위험": 정책의 강제는 MCP 기본 모드의 에이전트에게만 성립한다). MCP 서버는 `confirm.*`를 도구로 내놓지 않고 스스로 부르지도 않는다. CLI 명령(`pegboard confirm …`)은 3b에 만들지 않는다(제안. 셸이 있는 에이전트가 스스로 승인하기 쉬워질 뿐이라서).
- 결과: 거부된 명령은 `policy_denied`, `data = {"reason": …, "confirmId": …}`. 메시지는 사람이 읽는 한 줄: "a person denied this upload", "no answer within 60 s; denied", "confirmation needs the Pegboard browser (or a confirmation client); denied" 등. 허용된 명령의 결과에는 확인이 있었다는 것만 `confirmed: {by}`로 붙인다.
- 동작 기록: `ActionEntry`에 `confirm: {outcome, by, waitMs}`(묻지 않은 명령에는 없다). 거부된 명령은 지금처럼 명령 이름만 남기고 이 필드를 더한다. 확인 창에 보인 내용은 기록에 넣지 않는다(쿠키 값 같은 비밀이 들어 있다. 기존 가림 규칙을 따른다).
- 구현에서 정한 것: 기다린 명령의 기록 줄은 답이 온 때가 `ts`이고 `durationMs`는 그때부터 잰다(기다린 시간은 `confirm.waitMs`. 녹화에서 명령이 대기만큼 길어 보이지 않게). 구독자는 8개까지(`limit_exceeded`), 알림을 10초 안에 받지 않는 구독자는 끊는다. 닫히는 중인 세션이 뒤늦게 묻는 것은 바로 `cancelled`(닫기가 세션을 닫는 중으로 표시해 둔다). `confirm.resolved`는 표의 자물쇠 안에서, 브라우저 창을 닫기 전에 보낸다. 브라우저는 자기가 아직 보이는 확인에만 답할 수 있다(아니면 `confirm_not_found`). 오류의 `reason`은 snake_case, 알림과 기록의 `outcome`은 camelCase다(architecture.md 7절).

### 4.3 업로드 (B11)

| 정책 | 묻나 | 에이전트가 주는 것 | 파일을 찾는 곳 | 프록시가 받는 폴더 |
|---|---|---|---|---|
| `--allow upload --upload-dir D` | 아니 | 맨 이름 | `D`, 세션 파일 디렉터리 (지금 그대로) | `D`, 세션 파일 디렉터리 |
| 묻기 + `--upload-dir D` | 예 | 맨 이름 | `D`, 세션 파일 디렉터리 | 그 명령 동안 사본 폴더만 |
| 묻기, 폴더 없음 | 예 | 맨 이름 또는 절대 경로 | 맨 이름은 세션 파일 디렉터리, 절대 경로는 그 경로 | 그 명령 동안 사본 폴더만 |
| `--deny upload` | 아니 | — | — | 없음 |

- 절대 경로의 검사(묻기, 폴더 없음): 마지막 이름이 심볼릭 링크면 거부(지금 규칙과 같다), 실제 경로가 일반 파일이어야 하고, pegboard 홈(다른 세션의 파일, 녹화, 설정)과 브라우저 사용자 데이터 디렉터리 안이면 거부, 파일 하나 200 MiB(다운로드 한도와 같다), 한 명령 16개까지. 사람에게 보이는 것은 실제 경로다.
- **사본(TOCTOU 대응)**: 확인을 띄우기 **전에** 데몬이 각 파일을 `O_NOFOLLOW`로 열고 연 파일에서 `fstat`으로 다시 보고(일반 파일, 크기) 그 열린 파일에서 `<PEGBOARD_HOME>/sessions/<id>/confirm/<confirmId>/<원래 이름>`(0700)으로 복사한다. 창에는 원래 실제 경로와 사본의 크기를 보인다. 승인되면 agent-browser는 사본 경로로 올리고, 페이지가 보는 파일 이름은 원래 이름이다. 승인 뒤 원본이 바뀌거나 링크로 바뀌어도 올라가는 것은 확인을 띄울 때의 내용이다. 사본 폴더는 `files.list`에 보이지 않는다.
- **사본을 언제 지우나**: 처음 제안은 "명령이 끝나면 지우고, 세션을 닫을 때와 데몬이 시작할 때 남은 것을 지운다"였다. 브라우저는 입력의 파일을 늦게(폼을 보낼 때) 읽어서, 명령이 끝날 때 지우면 나중의 폼 제출이 실패했다(측정, 시험 `an_approved_upload_is_sent_when_the_form_is_submitted_later`). 그래서 **실행된 업로드의 사본은 세션이 닫힐 때까지 둔다**: 세션 4 GiB, 데몬 전체 8 GiB 예산 안에서(넘으면 그 세션의 오래된 사본부터, 승인 뒤에만 지운다), 남은 디스크가 1 GiB보다 적으면 사본을 뜨지 않는다. 실행되지 않은 명령(거부, 시간 초과)의 사본은 곧 지우고, 세션 닫기와 데몬 시작이 남은 것을 지운다. 사본은 검사한 파일 기술자에서 APFS 복제로 뜨고(안 되면 바이트 복사), 같은 파일을 두 번 주면 한 번만 뜬다. 디렉터리는 0700, 파일은 0600.
- **거부하는 곳을 넓혔다**(보안 검토): 처음 제안의 "pegboard 홈과 브라우저 사용자 데이터 디렉터리" 말고도 브라우저들의 캐시(`~/Library/Caches`의 짝), agent-browser의 `/tmp/pegboard-<uid>`, 포크의 저장된 창 상태, `/dev`. 디렉터리는 이름과 함께 그 위 디렉터리마다의 장치·inode로도 맞춘다(펌링크처럼 이름이 둘인 디렉터리). 경로 글자는 평범한 꼴만(빈 이름, `.`, `..`, 제어·서식·양방향·보이지 않는 문자, 역슬래시, 오른쪽에서 왼쪽 글자, 결합 문자, 빗금 닮은 글자, 특수 공백이 없고 1,023바이트까지). 파일은 `O_NOFOLLOW | O_NONBLOCK`로 열고 그 기술자에서 다시 본다(일반 파일, 링크 수 1, 경로가 가리킨 그 파일, `F_GETPATH`의 실제 경로). 절대 경로는 묻기 + 폴더 없음 세션에서만 받는다(`--allow upload`나 `--upload-dir` 세션은 `argv_rejected`).
- 응답자가 아무도 없으면 파일을 보기 전에 거부한다(`an_upload_with_nobody_to_answer_is_denied_before_its_files_are_read`).
- 묻기 모드에서 프록시의 업로드 폴더(`set_upload_dirs`)는 평소 비어 있고, 승인된 명령 동안만 그 명령의 사본 폴더 하나다. 그래서 세션 엔드포인트에 직접 붙은 클라이언트도 승인되지 않은 파일은 올릴 수 없다(지금 묻기 없는 `--upload-dir`은 폴더 전체를 연다).
- "이 세션에서 계속 허용"은 **`--upload-dir`이 있을 때만** 내놓는다. 받은 뒤 그 세션은 `--allow upload --upload-dir D`처럼 동작한다. 폴더가 없을 때 이것을 주면 그 뒤 아무 경로나 묻지 않고 올라가므로 내놓지 않는다.
- 창이 보이는 "대상 페이지 출처"는 확인을 띄울 때 agent-browser가 붙은 탭의 주 프레임 출처다. 승인 뒤 실행 바로 전에 다시 보고 다르면 `stale`로 거부한다.
- 결과에서 경로를 지우는 규칙(`hide_paths`)은 사본 경로에도 건다.
- **승인하면 누가 읽나**: 페이지에 들어간 파일의 내용은 **에이전트**(주 세계에서 `Runtime`으로 `input.files`를 읽는다)와 **보인 페이지의 출처**가 읽을 수 있다. 출처 고정은 브라우저가 파일을 어디에 넣는지를 정할 뿐, 누가 읽는지를 정하지 않는다. 그래서 창의 업로드 내용 끝에 "읽을 수 있는 쪽: 허용하면 이 파일의 내용을 에이전트와 <출처> 페이지가 읽을 수 있습니다" 줄이 있다(데몬의 `details`, 보안 재검토 I-2).
- **거부 이유는 가리고, 있음은 가리지 않는다**: 에이전트가 받는 거부는 파일마다 같은 문구(`upload::NOT_TAKEN`)이고 이유(링크, 일반 파일 아님, 홈 안, 크기)는 데몬 기록에만 남는다. 그러나 에이전트는 그 경로가 묻기 전에 거부되었는지, 확인이 떴는지(혹은 시간 초과)를 구분할 수 있으므로, 절대 경로의 파일이 있고 받을 만한지는 숨겨지지 않는다(남는 위험, 재검토 M-4).
- **프록시의 업로드 검사 세계** (재검토 I-1): 승인된 창 안의 `DOM.setFileInputFiles`는 프록시가 먼저 노드를 본다. 검사마다 이름이 무작위(`pegboard-upload-check-` + 128비트)인 새 격리 세계를 만들어(이름이 같으면 Blink가 같은 세계를 돌려주므로, 에이전트가 미리 만들거나 이름으로 찾지 못하게), 그 세계의 `Runtime.executionContextCreated`/`Destroyed`와 그 컨텍스트를 가리키는 `Runtime.*` 이벤트를 클라이언트에 넘기지 않고, 그 컨텍스트(id, uniqueId)나 그 안의 객체(`objectId`의 가운데 수)를 가리키는 클라이언트 호출(`Runtime.evaluate.contextId/uniqueContextId`, `Runtime.callFunctionOn.executionContextId/uniqueContextId/objectId/arguments[].objectId`, `DOM.resolveNode.executionContextId` 등)과 그 이름의 `Page.createIsolatedWorld`를 거부한다. 검사가 도는 동안은 컨텍스트나 객체를 가리키는 호출을 모두 거부한다(프록시가 아직 모르는 새 컨텍스트일 수 있다). 스크립트와 상관없는 구조 검사로 `DOM.describeNode`가 `<input>`이고 `type` 속성이 `file`이어야 한다. 노드가 탭의 최상위 문서에 있는지는 그 세계의 스크립트가 본다: 156의 `DOM.describeNode`는 입력 요소의 문서·프레임을 주지 않고(`frameId`는 프레임 소유 요소와 문서 바로 아래 요소에만), 문서 트리를 읽는 `DOM.getDocument`는 클라이언트의 노드 ID를 모두 버리게 하기 때문이다(처음 제안은 구조 검사로 `frameId`까지 보는 것). 창마다 세대 번호가 있어 검사 중에 명령이 끝나거나 다른 창이 열리면 넘기지 않고, 노드 객체는 검사의 객체 그룹에 두었다가 쓴 뒤 놓는다. 창의 탭은 확인을 띄울 때의 탭이고(실행 때 다시 고르지 않는다), 승인 전 출처 검사도 그 탭으로 한다. 사본 예산을 위해 오래된 사본을 지우는 것은 승인 뒤에만 하고, 남은 디스크 공간은 예산보다 먼저 본다.

### 4.4 state

| 명령 | 창에 보이는 것 | 승인 뒤 실행 |
|---|---|---|
| `cookies set <이름> <값> [--url/--domain/--path …]` | 쿠키 이름, 값(200자까지), 적용될 도메인·경로(`--url`/`--domain`이 있으면 그것, 없으면 지금 탭의 출처), 플래그 | `--url`·`--domain`이 없던 명령은 확인을 띄울 때의 탭 주소를 `--url`로 넣어 실행한다(출처 고정) |
| `storage local\|session set <키> <값>` | 출처, 저장소 종류, 키, 값(200자까지) | 실행 바로 전에 탭의 출처가 같은지 보고, 다르면 `stale` |
| `storage local\|session clear` | 출처, "이 출처의 localStorage(또는 sessionStorage) 전체 삭제" | 같은 출처 검사 |

- 출처 검사와 agent-browser의 실행 사이의 짧은 틈은 남는다(남는 위험). 쿠키는 `--url`로 넣어 틈이 없다.
- **쿠키 창의 머리와 경로**: 창의 첫 줄은 풀어 낸 호스트(`호스트`, 길면 왼쪽을 자른다)다. `--path`가 없는 명령은 창에 보인 경로(주소의 RFC 6265 기본 경로, 도메인만이면 `/`)를 넣어 실행한다. Chrome의 `setCookie`는 경로 없는 `url`에 `/`를 써서, 창에 보인 경로와 실제가 달랐다(실측). 사용자 이름·비밀번호가 든 `--url`, 253자를 넘는 호스트, 두 번 준 값 플래그는 문법이 거부한다.
- **출처를 모르면 묻지 않는다**: 탭의 주소를 읽을 수 없을 때(탭 여럿 중 고른 것이 없음, 2초 안에 못 읽음), 출처가 불투명할 때(`about:blank`, `about:srcdoc`, `data:`)는 묻지도 실행하지도 않고 `policy_denied`(`reason: unknown_origin`, 탭을 고르라는 안내)다. 처음 제안의 이유 값 다섯에 이것이 더해졌다.
- **프레임**: 처음 제안은 출처를 따로 다루지 않았고, 구현 중간에는 agent-browser가 고른 프레임(`frame <선택자>`)의 출처를 `eval`로 읽어 보이고 고정했다. 실측(agent-browser 0.42.0): `eval`, `storage local set`, `cookies set`은 프레임을 골라도 탭의 최상위 프레임에서 돌고, `upload`(와 `is visible`)만 고른 프레임에서 요소를 찾는다. 그래서 창은 **탭의 출처만** 보이고 고정하며, 데몬이 `frame <선택자>`/`frame main`을 따라가다 프레임이 골라져 있는 동안 묻는 저장소 쓰기와 업로드는 묻지 않고 바로 거부한다(`unknown_origin`, "`frame main`을 먼저"). 쿠키는 탭 주소로 고정하고 그대로 묻는다(`a_write_or_upload_in_a_selected_frame_is_refused_without_asking`). 스냅숏 ref가 `frame` 없이 iframe 안의 입력에 닿는 것도 실측해, 승인된 업로드는 탭의 최상위 문서의 파일 입력에만 들어간다(`an_upload_through_a_ref_into_an_iframe_is_refused`, 4.3의 검사 세계).
- 사람이 답한 뒤 요청 가드와 프로필 보호를 다시 본다(기다리는 동안 바뀌었을 수 있다).
- `eval`로 하는 쓰기는 묻지 않는다(지금처럼. 막으려면 `--deny eval`).

### 4.5 브라우저 쪽: `Pegboard` 도메인과 확인 창

**도메인 추가** (`pegboard_protocol.pdl`, 주인 세션만, F12 그대로):

| 메서드·이벤트 | 하는 일 |
|---|---|
| `requestConfirmation {confirmId, browserContextId, targetIds, sessionId, sessionName, profileDirectory, actionClass, details:[{label, value}], offerAllowForSession}` → `{}` | 창을 띄우고 바로 답한다(답은 이벤트로). 창이 뜰 곳: `targetIds` 중 처음 찾은 탭의 창, 없으면 그 컨텍스트의 가장 최근 일반 창. 둘 다 없으면 `-32000` |
| `cancelConfirmation {confirmId}` → `{}` | 그 창을 닫는다. 이미 없으면 그냥 성공 |
| 이벤트 `confirmationAnswered {confirmId, answer}` | `approve` \| `deny` \| `allowForSession`. 창을 닫은 것(Esc, 창 닫기, 그 탭이나 창이 닫힘)은 `deny` |

- 검사: 컨텍스트와 탭이 에이전트 프로필 것이 아니면 거부(F10의 규칙 그대로). `confirmId`는 32자리 소문자 16진수, 열린 창의 ID와 겹치면 거부. 동시에 열린 창 16개까지. `details`는 40줄, 한 값 1,000자까지. `actionClass`는 `upload`, `state`만.
- 주인이 바뀌거나 떨어지면(데몬 재시작) 열린 확인 창을 모두 이벤트 없이 닫는다. 새 데몬은 이전 확인을 모른다.
- 창 하나에는 자기 안전 시간(75초)이 있어, 데몬이 취소를 보내지 못해도 닫힌다(이벤트 없이).
- 구현에서 정한 것(작업 7): `targetIds`는 **모두** 그 프로필의 열린 에이전트 탭이어야 하고(하나라도 닫힌 탭, 사람 탭, 다른 프로필의 탭이면 `-32000`), `profileDirectory`는 컨텍스트의 실제 디렉터리와 같아야 한다. 창은 닫히는 중이 아닌 첫 탭의 창, 탭이 없으면 그 프로필의 가장 최근 일반 창. `sessionId`는 ASCII 글자·숫자·`_`·`-` 64자 이하, 라벨은 40자 이하. 한 창에는 확인 창을 하나씩만 띄우고 같은 창의 다른 요청은 요청 순서로 기다린다(기다리는 동안에도 16개 한도와 75초에 든다). 지켜보던 탭 하나라도 닫히거나 다른 창으로 옮겨지면, 창이 닫히면(떠 있던 것과 기다리던 것 모두) `deny`.

**확인 창** (`//pegboard/ui`):
- **에이전트 창의 자식 창**(`views::DialogDelegate::CreateDialogWidget`, `ModalType::kNone`, 부모는 에이전트 창의 위젯, 그 창 위쪽 가운데). 처음 제안은 브라우저 창 모달 대화상자(`constrained_window::CreateBrowserModalDialogViews`, `ModalType::kWindow`)였다. 맥에서 그것은 에이전트 창의 시트이고, AppKit이 시트를 띄우면서 키 창으로 만들어 사람 창의 키보드 초점을 가져갔다(실측: 띄운 직후 키 창 `Default`, 200ms 뒤 `sheet:PegboardAgent`. `ShowInactive`도 시트에는 효과가 없다). 5절 위험 1의 대안(탭 띠 아래 막대)까지 가지 않고 모달이 아닌 자식 창으로 풀었다. 대가: 창이 떠 있는 동안 사람이 에이전트 창의 탭을 쓸 수 있다(막지 않는다). 여전히 브라우저 UI이고 웹 콘텐츠의 대화상자(JavaScript `confirm`)가 아니다. 그래서 `Page.handleJavaScriptDialog`(agent-browser의 `dialog accept`)가 닿지 않고, 에이전트의 `Input.dispatch*`는 탭의 렌더러로만 가서(3a 작업 10 후속: 브라우저 단축키와 메뉴를 거치지 않는다) 창 버튼에 닿지 않는다.
- **비활성으로 띄운다**(`ShowInactive`). 앱 활성화, 창 앞으로 가져오기, 키 창 바꾸기를 하지 않는다. 그 창이 최소화되어 있으면 최소화된 채로 둔다(사람은 Dock 튕김으로 안다, B10).
- 기본 버튼은 **거부**. Esc와 창 닫기도 거부. 세 버튼은 창이 보인 뒤 1초 동안 눌리지 않는다(사람이 치던 키나 클릭이 승인으로 바뀌지 않게). 처음 제안은 1초뿐이었다. 보안 검토에서 바꿨다: 맥의 views 창은 비활성이어도 첫 클릭을 받으므로, 페이지가 사람에게 같은 자리를 계속 누르게 하면 1.0초 뒤의 클릭이 승인이 될 수 있었다. 그래서 잠금은 **보인 뒤 최소 1초, 그리고 확인 창 위의 키·클릭이 500ms 없을 때까지**이고, 버튼이 켜진 뒤 500ms 동안의 누름과 화면 속 화면 창이 확인 창을 가리는 동안의 누름도 무시한다. 잠긴 동안 버튼은 비활성이다.
- 문구(B14): 제목 "에이전트가 확인을 요청합니다", 첫 줄 "세션 «이름» (s_xxxxxxxx) · 프로필 <디렉터리>"(처음 제안. 만든 것: 첫 줄은 굵은 `세션 <ID> · 프로필 <디렉터리>`로 데몬과 브라우저가 아는 것만, 이름은 둘째 줄 흐린 글씨 `에이전트가 붙인 세션 이름: «…»`이고 이름 안의 `« » ( ) ·`도 바꾼다. 이름에 `» (s_…) · 프로필 Default «`를 넣어 머리줄을 흉내 낼 수 있었다), 둘째 줄 분류별 문장("파일 2개를 https://example.com 에 올리려 합니다" / "https://example.com 의 쿠키를 쓰려 합니다"), 그 아래 `label: value` 줄들, 끝에 "60초 안에 답하지 않으면 거부됩니다". 버튼 "허용", "거부", "이 세션에서 계속 허용"(내놓을 때만).
- 에이전트가 정할 수 있는 글(세션 이름, 파일 이름, 쿠키 이름·값, 키)은 평문 라벨로만 보인다. 데몬이 보내기 전에 제어 문자와 양방향 서식 문자(U+202A~202E, U+2066~2069, U+200E/F 등)를 `\u{…}` 꼴로 바꾸고 길이를 자른다. 브라우저도 같은 규칙으로 한 번 더 거른다(두 번째 벽). 파일 확장자를 오른쪽에서 왼쪽 문자로 숨기는 속임을 막는다.
- 세션 이름은 에이전트가 고를 수 있으므로 창은 언제나 세션 ID와 프로필 디렉터리를 같이 보인다.
- 경로(`파일`, 쿠키의 `경로`)는 라벨 방향을 LTR로 고정하고 `/`마다 뒤에 U+200E를 넣는다(방향 고정만으로는 오른쪽에서 왼쪽 글자 디렉터리 둘이 한 덩어리로 뒤집혔다). 값은 자르지 않고 줄 바꿈으로 다 보이며 라벨 아래 들여 쓴다. 상세 줄이 많으면 그 부분이 스크롤된다(최소 160px, 최대 320px). 브라우저의 글 거르기는 데몬 규칙과 같되 역슬래시를 두 번 바꾸지 않는다(데몬이 이미 바꿔 보낸다).
- 브라우저 쪽 시험 훅은 GN 인자 `pegboard_test_hooks`(기본 거짓)가 참인 빌드에만 있다(처음 제안은 환경 변수 검사뿐). 개발·시험 빌드(`browser/args.gn`)만 켠다. 사람에게 줄 빌드에서는 환경 변수를 넣어도 자동 답이 없다.

**Dock 튕김**(B10): 창을 띄울 때 앱이 활성이 아니면 `requestUserAttention:NSInformationalRequest` 한 번. 활성이면 아무것도 하지 않는다.

### 4.6 에이전트 창 표시, 프로필 숨기기, 로그인과 비밀번호 관리자

**에이전트 창 표시 (B12)**: 도메인이 에이전트 프로필을 올리거나 만들 때(이미 하는 `OnProfileAdded`, `openProfileWindow`):
- 프로필 테마를 예약한 색 하나로 건다(Chromium의 사용자 색 테마: `ThemeService`의 사용자 색 설정. 156 함수 이름은 구현 때 확인). 제안 색: 짙은 호박색 계열(기본 회색·파랑 틀과 다르고 밝은·어두운 모드 둘 다에서 보인다. 정확한 값은 만드는 쪽이 고른다).
- 도메인이 여는 에이전트 창에 창 사용자 제목 "Pegboard 에이전트"를 건다(Chromium의 "창 이름 지정" 기능의 값). Mission Control과 창 메뉴에서 구분된다.
- 사람이 사람 프로필에 같은 색 테마를 고르는 것은 막지 않는다(남는 위험, 창 제목은 다르다).
- 3b 범위의 표시는 포크 모드에만 있다. 순정 모드는 그대로다.
- 만든 것(작업 8): 처음 제안은 "도메인이 에이전트 프로필을 올리거나 만들 때" 거는 것이었다. 만든 것은 `//pegboard/browser_parts`의 `AgentProfiles`가 **브라우저 시작부터**(데몬이 없어도) 건다. 테마는 프로필이 초기화될 때마다(`PostProfileInit`, 첫 창보다 먼저) 사용자 색 `#B45309`(짙은 호박색), 변형 `kVibrant`(`ThemeService::SetUserColorAndBrowserColorVariant`). 창 제목 "Pegboard 에이전트"는 도메인이 여는 창만이 아니라 그 프로필의 **모든 일반 창**(`OnBrowserCreated`, `WindowMetadataController::SetWindowUserTitle`)이다. 맥에서는 사용자 제목이 페이지 제목을 대신해 창 메뉴와 Mission Control에 "Pegboard 에이전트"만 보인다. 사람이 에이전트 프로필의 테마를 바꿔도 다음 시작에 돌아온다. 에이전트 프로필의 시크릿 창에는 제목이 없다(테마는 따른다).

**프로필 숨기기 (B17)**: 같은 시점에 에이전트 프로필의 `ProfileAttributesEntry`를 생략으로 표시한다. 생략된 프로필은 프로필 메뉴와 선택 화면에 나오지 않고, 시작 때 선택 화면을 띄울지 셀 때 빠진다(156에서 확인. 아니면 만드는 쪽이 같은 효과의 다른 기존 기능을 찾고, 없으면 멈추고 보고한다). 시작 때 지난번에 열려 있던 에이전트 프로필 창이 다시 열리는지(`last_active_profiles`) 함께 본다. 열리면 F11의 정리가 곧 닫지만 깜박인다: 고치기가 작으면(`//pegboard` 안에서 그 목록에서 빼기) 고치고, 아니면 열린 항목으로 남긴다.
- 만든 것(작업 8): `SetIsOmitted`는 저장되지 않는 메모리 값이라, 도메인이 아니라 `AgentProfiles`가 시작마다(`PreProfileInit`, 첫 프로필 전) 목록의 에이전트 항목을 모두 생략으로 두고 그 뒤 더해지는 것도 바로 생략한다(`ProfileAttributesStorage` 관찰자). 업스트림은 임시 프로필만 생략한다고 DCHECK하므로 DCHECK 빌드에서는 생략하지 않는다. **생략은 시작 때 선택 화면을 막지 못했다**(선택 화면 판정 `GetNumberOfProfiles`가 생략을 센다). 그래서 위 "아니면"의 길: Local State `browser.profile_picker_availability_on_startup`의 **기본값**을 사람 프로필이 하나 이하면 1(사용 안 함), 둘 이상이면 업스트림 기본 0으로 두고 프로필이 더해지고 지워질 때마다 다시 정한다(정책이 이긴다). 사람이 두 번째 프로필을 만들면 선택 화면이 다시 뜬다. **지난번 에이전트 창이 다시 열렸다**(`profile.last_used`가 에이전트): 시작 때만 `profile.last_used`를 사람 프로필로 되돌리고 `profile.last_active_profiles`에서 에이전트를 뺀다. 실행 중에 되돌리면 그 값이 DevTools의 기본 컨텍스트라 데몬의 다운로드 정책 걸기가 깨졌다(포크의 `session create` 실패).
- 작업 8~10 검토에서 찾은 것(3a부터): 데몬이 에이전트 탭을 활성화하면 에이전트 창이 주 창이 되어 맥 `AppController`의 마지막 프로필이 에이전트 것이 되고, **다른 앱에서 연 링크**(메일의 로그인 링크), 앱 메뉴의 설정과 새 창, 창이 없을 때의 Dock 클릭이 에이전트 프로필로 갔다(실측). `AgentProfiles`가 `NSWindowDidBecomeMainNotification`을 보고 마지막 프로필을 가장 최근 사람 창의 프로필로 되돌린다(`[AppController setLastProfile:]`, `//pegboard`만). 마지막 에이전트 창이 닫히면 `profile.last_used`도 사람 프로필로 돌린다.

**로그인과 비밀번호 관리자 (B13)**: `//pegboard`의 메인 파츠가 모든 프로필이 올라올 때 그 프로필의 설정 기본값을 바꾼다(`PrefService`의 기본값 바꾸기. 사용자가 고른 값은 그대로 이긴다). 바꿀 것과 대응하는 정책(156에서 이름 확인):

| 정책(참고) | 설정 | 값 |
|---|---|---|
| `BrowserSignin` = 0 | `signin.allowed` | false |
| `PasswordManagerEnabled` = false | `credentials_enable_service` | false |
| `AutoSignInEnabled`(참고) | `credentials_enable_autosignin` | false |
| 구글 비밀번호 관리자 패스키 | 156의 해당 설정 | 저장 제안 끔 |

- 정책 파일을 앱에 넣는 방식(관리형 환경설정)은 쓰지 않는다. macOS에서는 MDM 프로필이 있어야 읽히고, "조직에서 관리" 표시가 뜬다.
- 확장 프로그램(Bitwarden 등)의 동작에는 손대지 않는다. 사람 프로필과 에이전트 프로필 모두에 같은 기본값이 걸린다.
- 업스트림 줄을 늘리지 않으려고, 3a의 부트스트랩 연결 한 줄이 넣는 메인 파츠를 `pegboard::DaemonLauncher`에서 `pegboard::MainParts`(데몬 실행기, 기본값, 알림을 거느린다)로 바꾼다. 업스트림 줄 수는 같다.
- 만든 것(작업 9): 처음 제안은 "모든 프로필이 올라올 때"(`ProfileManagerObserver`) 기본값을 바꾸는 것이었다. 로그인 허용은 프로필의 서비스를 만들 때 한 번 정해져(`AccountConsistencyModeManager`) 그때는 늦다(5절 위험 5가 실제로 일어났다). 그래서 서비스 없는 키드 서비스 팩토리(`ProfileDefaults`)의 `RegisterProfilePrefs`에서 레지스트리 기본값을 바꾼다(`PrefRegistry::SetDefaultPrefValue`, 그 설정을 등록하는 팩토리들에 `DependsOn`). 설정은 다섯: `signin.allowed_on_next_startup`(설정 화면의 스위치, 시작마다 `signin.allowed`로 옮겨진다), `signin.allowed`, `credentials_enable_service`, `credentials_enable_autosignin`, `credentials_enable_passkeys`. 설정 이름이 바뀌어 없으면 시작에서 `CHECK`로 멈춘다(조용히 다시 켜지지 않게). 정책이 아니므로 `chrome://management`는 "관리되지 않음"이다. 이 빌드는 구글 OAuth 클라이언트가 없어 원래 로그인을 못 한다(`signin.allowed`가 늘 거짓). 업스트림 줄은 늘지 않았다.

### 4.7 문자열과 아이콘

**문자열 (B15)**: Chromium은 제품 이름이 들어간 문자열을 `chromium_strings.grd`(브라우저)와 `components_chromium_strings.grd`(컴포넌트)에 모아 둔다. 3a는 그중 `IDS_PRODUCT_NAME` 둘만 바꿨다. 나머지(설정의 "Chromium 정보", 기본 브라우저 문구 등)는 많아서 손으로 쓴 패치로 두면 예산을 크게 쓰고 버전마다 충돌한다.
- `browser/scripts/rebrand-strings.py <src>`가 두 `.grd`와 그 `.xtb` 번역의 제품 이름 "Chromium"을 "Pegboard"로 바꾼다. `apply.sh`가 패치를 모두 얹은 뒤 돌리고 결과를 커밋 하나(`rebrand-strings (generated)`)로 남긴다. `export.sh`는 이 커밋을 패치로 뽑지 않는다. `budget.sh`는 이 커밋을 손 패치 예산과 따로 센다.
- **번역 ID**: `.xtb`의 번역은 영어 원문의 지문(grit의 메시지 ID)으로 이어진다. 원문만 바꾸면 ID가 바뀌어 번역이 끊기고 한국어 화면이 영어로 돌아간다. 스크립트는 트리의 grit 지문 함수로 바꾸기 전후 ID를 계산해 `.xtb`의 `id`도 같이 바꾼다.
- 바꾸지 않는 것: 저작권과 저작자("The Chromium Authors"), 오픈 소스 고지, `chromium.org` 주소, ChromeOS 이름. 스크립트의 제외 목록으로 둔다. 바꾼 메시지 수와 제외한 수를 출력한다.
- 만든 것(작업 6): 바꾼 메시지 693개(673 + 20), 번역 ID 612개, 생성 커밋 파일 165개. 오픈 소스 고지는 처음 제안처럼 메시지를 통째로 빼지 않고 Chromium 프로젝트 링크(`BEGIN_LINK_CHROMIUM`~`END_LINK_CHROMIUM`) 안만 남겨 "Pegboard는 Chromium 오픈소스 프로젝트를 비롯한…"이 된다. 한국어는 받침에 맞춰 이름 바로 뒤의 조사를 고친다(이/가, 을/를, 은/는, 과/와, 으로/로). 문자열만 바뀐 빌드는 47초였다(메시지 번호가 그대로라 `branded_strings.h`가 다시 쓰이지 않는다). 두 대상 `.grd` 밖의 문구("Google Chrome 도움말" 같은 것)와 웹 UI의 로고 그림은 그대로다(10절).

**아이콘**: `browser/branding/icon.swift`를 다시 그린다. 둥근 사각형 위의 페그보드(구멍 격자)와 페그 하나, macOS 아이콘 격자(바깥 여백 포함), 16px에서도 형태가 보인다. 그림의 세부는 만드는 쪽이 정한다. 생성 흐름(`make-icons.sh` → `mac/app.icns`, `mac/Assets.car`)은 3a 그대로다.

**데몬 포기 알림 (B16, 만든 것)**: `//pegboard/ui/daemon_notice`. 제목 "Pegboard 에이전트 데몬이 멈췄습니다", 본문 "데몬이 1분 안에 네 번 끝나서 다시 띄우지 않습니다. 에이전트 기능을 다시 쓰려면 다시 시작하세요.", 버튼 "다시 시작" / "닫기"(기본 버튼과 Esc는 닫기). 처음 제안(계획)은 정적 `Show`/`CloseIfShown`, 아무 프로필의 마지막 창, 브라우저 모달이었다. 만든 것은 확인 창처럼 모달이 아닌 자식 창을 비활성으로(시트는 키 창을 가져간다), 자리는 B16대로 **사람 프로필**의 가장 최근에 활성이던 일반 창(시크릿 포함, 사람 창이 없으면 다음에 열리는 사람 창), `DaemonLauncher`가 알림 객체를 쥔다(지우면 닫힘, 종료 때 함께 닫힘). "다시 시작"은 재시작 기록을 비우고 데몬을 띄우며 뜬 뒤 1초 동안 비활성이다. 데몬이 다시 뜨면 열린 알림은 닫힌다. 알림이 떠 있던 사람 창이 닫히면(종료가 아니면) 다음 사람 창에 다시 뜬다. 앱이 앞에 없으면 Dock을 한 번 튕긴다.

### 4.8 시험

- **이 기기(브라우저 없음)**: 정책 판정표, 중개자(경쟁, 세션 묶기, 끝나는 길 모두, 응답자 없음), API 구독·목록·응답, 클라이언트 읽기 제한, 업로드 경로 검사와 사본, state의 출처 고정, 글 거르기, 동작 기록의 `confirm` 필드, 도메인 판 브리지의 새 메서드(가짜 브라우저).
- **맥미니, 순정 구성**: 실제 브라우저로 묻기 → API 구독자가 답 → 명령이 이어짐 / 거부 / 시간 초과(시험 훅 `PEGBOARD_TEST_CONFIRM_TIMEOUT_MS`로 줄임) / 세션 닫기. 응답자가 없으면 바로 `no_responder`. CLI·MCP 판(`pegboard-cli`의 시험 하네스는 순정만 지원한다).
- **맥미니, 포크 구성**: 확인 창이 그 세션의 에이전트 창에 뜨고, 시험 훅이 버튼을 누르고, 결과가 데몬에 온다. 창의 내용, 초점(창이 뜬 뒤에도 사람 창이 키 창이고 앞 앱이 그대로), 에이전트의 입력과 `dialog accept`가 창을 풀지 못함, 두 세션의 창이 섞이지 않음, 데몬 재시작이 창을 닫음, 표시·숨기기·기본값·문자열, 데몬 포기 알림과 다시 시작.
- **브라우저 쪽 시험 훅**: 브라우저 자신의 환경에 `PEGBOARD_TEST_HOOKS`가 있을 때만 읽는다. `PEGBOARD_TEST_DIALOG_LOG=<파일>`: 창을 띄울 때마다 한 줄 JSON(종류, 보인 글 전부, 창의 프로필, 띄운 직후와 200ms 뒤의 키 창 프로필과 앱 활성 여부). `PEGBOARD_TEST_DIALOG_ANSWER=<버튼>`: 1초 잠금이 풀린 뒤 그 버튼의 처리 함수를 부른다(`approve`, `deny`, `allowForSession`, `none`(누르지 않음), 알림 창의 `restart`, `close`). 제품 실행(Dock, `open`)에는 이 변수가 없고, 3a의 부트스트랩은 브라우저 환경에 `PEGBOARD_TEST_HOOKS`가 없으면 `PEGBOARD_TEST_*`를 데몬에게도 넘기지 않는다. 데몬에는 자동으로 답하는 훅이 없다.
- 모든 C++ 변경에는 변형 확인("이 줄을 이렇게 바꾸면 시험 X가 실패한다")을 붙이고, 보안에 닿는 것(도메인 메서드, 확인 창의 입력 처리, 시험 훅의 문)은 따로 검토자를 둔다(3a와 같다).

### 4.9 빌드와 예산

- 개발 기기의 Chromium 트리(`156.0.8078.109`, 브랜치 `pegboard-work`), `browser/scripts/{apply,export,build,package-dev,budget}.sh`. 빌드는 언제나 `-j 8`(전체 병렬에서 기기가 커널 패닉으로 멈췄다), 도구 시간 제한에 끊기지 않게 떼어 돌린다. 증분 30초~3분, 전체 다시 빌드 약 2시간 45분.
- 문자열 바꾸기는 생성 리소스와 그것을 포함하는 파일을 다시 컴파일하게 한다. 메시지 번호(숫자 ID)는 바뀌지 않으므로 헤더가 같으면 다시 컴파일이 적을 것이다 [미확인]. 첫 빌드 때 잰다.
- 업스트림 예산: 3a 끝 15개 파일, 120줄(그중 45줄은 157 이상에서 지울 클립보드 패치). 3b가 더할 손 패치 줄의 목표(제안): **15줄 이하**. 예상 내역: `pegboard-cdp-domain.patch`의 `async` 목록에 메서드 없음(새 메서드는 모두 동기 응답) 0줄, `//pegboard/ui` 의존을 위한 BUILD.gn 몇 줄, 메인 파츠 이름 바꾸기 0줄. 생성 커밋(문자열)은 따로 센다. 패치마다 줄 수를 기록한다.

## 5. 위험과 측정할 것

1. **창을 비활성으로 띄울 수 있나.** 맥에서 창 모달 대화상자(시트)를 비활성 창에 붙이면 앱이 활성화되거나 그 창이 앞으로 올 수 있다 [미확인]. 시험 훅의 키 창 기록으로 잰다. 안 되면 대화상자 대신 그 창의 탭 띠 아래 막대(브라우저 UI, 웹 콘텐츠 밖)로 바꾸고, 그것도 초점을 가져가면 멈추고 사용자에게 묻는다.
2. **`//pegboard/ui`의 빌드 의존.** `//chrome/browser/ui/views` 쪽 헤더를 쓰는 `//pegboard` 타깃은 `//pegboard/devtools`처럼 `check_includes = false`로 돌아가야 할 수 있다. 업스트림 BUILD.gn 줄이 늘면 기록한다.
3. **번역 ID 다시 쓰기.** 지문 계산이 grit과 하나라도 다르면 번역이 조용히 영어로 돌아간다. 시험이 한국어 화면의 문자열로 확인한다.
4. **프로필 생략의 효과.** 156에서 생략이 선택 화면과 시작 판정까지 덮는지. 4.6의 대안 규칙.
5. **기본값을 바꾸는 시점.** 프로필이 올라온 뒤 기본값을 바꾸면 그 전에 이미 값을 읽은 화면(예: 첫 창의 프로필 메뉴)은 옛 값을 볼 수 있다. 시험이 첫 창에서 확인한다. 늦으면 프로필 설정 등록 시점에 거는 다른 길을 찾고, 업스트림 줄이 들면 기록한다.
6. **기다리는 명령과 MCP 클라이언트의 시간 제한.** 어떤 MCP 클라이언트는 도구 호출을 60초 안팎에서 끊는다. 그 경우 명령은 데몬에서 끝까지 가지만 에이전트는 결과를 못 본다. 문서에 적는다.

## 6. 만드는 쪽에 맡긴 것과 정한 값

- 맡긴 것: 확인 창을 만드는 Chromium API(4.5), 사람이 알아채는 추가 방법(B10의 조건 안에서), 테마 색의 정확한 값, 아이콘의 그림, 기본값을 거는 정확한 시점, 패스키 설정의 이름, 문자열 제외 목록의 세부.
- 정한 값(제안): 확인 시간 60초(사용자), 브라우저 창의 안전 시간 75초, 버튼 잠금 1초, 동시에 열린 확인 창 16개, `details` 40줄·값 1,000자, 창에 보이는 쿠키·저장소 값 200자, 업로드 파일 하나 200 MiB·한 명령 16개, `confirmId` 128비트.

- 모든 C++ 변경에 변형 확인이 있고, 보안에 닿는 작업은 따로 검토받았다.
- 패치별 업스트림 줄 수와 생성 커밋의 크기, 빌드 시간을 기록했다.
- architecture.md(11절 권한 표와 기본 정책, 7절 API 표와 메시지, 남는 위험), roadmap.md(할 일 5, 7), README(정책 옵션, 확인 창), `browser/README.md`(문자열 스크립트, 아이콘)를 고쳤다.

## 8. 남는 위험

설계 때 보인 것:
- 같은 사용자의 프로세스는 `confirm.respond`로 답할 수 있다(4.2. 지금의 `session.create`와 같은 수준).
- `storage … set/clear`의 출처 검사와 실행 사이의 짧은 틈(4.4).
- 확인 창이 떠 있는 창이 사람 눈에 안 보이면(다른 데스크톱, 최소화) 60초 뒤 거부된다. 안전한 쪽이지만 에이전트의 작업이 멈춘다.
- 사람이 사람 프로필에 에이전트와 같은 테마 색을 고를 수 있다(창 제목은 다르다).
- 사람이 설정에서 비밀번호 관리자와 로그인을 다시 켤 수 있다(의도한 것: 기본값만 바꾼다).

만들며 드러난 것:
- 같은 사용자의 셸과 손쉬운 사용(Accessibility) 권한을 가진 에이전트는 확인 창의 버튼을 직접 누를 수 있다(`AXPress`). 시험 훅과 같은 길이 아니라 OS의 길이라 막지 않는다. 셸을 가진 에이전트는 이미 사람의 권한이다(architecture.md 11절).
- 화면 속 화면이 아닌 다른 앞쪽 창(페이지가 위치를 정해 연 팝업 등)이 확인 창을 가리는 것은 막지 않는다. 가린 채로 사람이 누르게 만들 수 있는지는 재지 않았다.
- 확인 창은 에이전트 창을 막지 않는다(자식 창, 4.5). 떠 있는 동안 사람이 에이전트 탭을 쓸 수 있다.
- 업로드를 승인하면 그 파일의 내용을 에이전트와 그 페이지의 출처가 읽는다(창이 말한다). 묻기 전에 거부된 파일의 이유는 가리지만, 그 경로에 받을 만한 파일이 있는지는 에이전트가 알아낼 수 있다(4.3).
- 실행 중 창이 하나도 없을 때 Dock을 누르면 마지막으로 쓴 에이전트 프로필의 창이 열릴 수 있다(`profile.last_used`는 실행 중 DevTools의 기본 컨텍스트라 에이전트 창이 있는 동안은 두고, 마지막 에이전트 창이 닫힐 때 되돌린다).
- 사람의 유일한 프로필을 지우면 업스트림이 다음 프로필로 넘어가는데, 그것이 에이전트 프로필일 수 있다(`delete_profile_helper.cc`).
- 에이전트 창의 프로필 메뉴에는 그 에이전트 프로필 자신이 보인다(생략은 "다른 프로필" 목록에만 걸린다). 임시가 아닌 프로필의 생략은 업스트림이 의도하지 않은 조합이라, 버전을 올릴 때 `IsOmitted()`를 읽는 곳을 다시 본다.
- 사람 프로필이 하나일 때 선택 화면의 "시작할 때 표시" 선택이 보이지 않고, `--profile-email`로 선택 화면을 여는 길이 막힌다(4.6 기본값).
- 알림이 떠 있는 사람 창을 사람이 닫으면 다음 사람 창에 다시 뜨지만, 알림을 "닫기"로 닫으면 데몬은 없는 채로 간다(브라우저를 다시 켜거나 다음 포기까지). 다시 시작 버튼에는 확인 창의 잠금 규칙 대신 1초 비활성만 있다(누르면 데몬이 다시 뜰 뿐이다).
- 어떤 MCP 클라이언트는 도구 호출을 60초 안팎에서 끊는다(5절 위험 6). 그러면 명령은 데몬에서 끝까지 가지만 에이전트는 결과를 못 본다.

## 9. 결과

2026-11-25 하루에 계획의 작업 11개를 끝냈다(Rust 1~5, Chromium 6~10, 정리 11). 측정과 시험 결과는 spike-findings.md "3b 작업 6" ~ "3b 작업 11".

- **2절의 목표**: 모두 시험으로 고정했다. 묻기(`upload`, `state`)와 `--allow`/`--deny`, 중개자와 `confirm.*` API(순정 구성에서 API 구독자가 답한다), 확인 창(포크 구성에서 시험 훅이 진짜 버튼 처리 함수를 누른다), 동작 기록의 `confirm`, 에이전트 창 표시와 프로필 숨기기, 로그인·비밀번호 관리자 기본값, 제품 이름 문자열(영어, 한국어), 아이콘(파일이 같은지까지. 화면은 사람이 본다), 데몬 포기 알림과 다시 시작.
- **2절의 실패 조건**: 페이지·에이전트가 확인을 풀지 못함(`agent_input_cannot_answer_the_dialog`, `proxy_refuses_pegboard_confirmation_methods`, `mcp_has_no_confirmation_tool`), 세션 A의 답이 B를 풀지 못함(`an_answer_for_session_a_does_not_release_session_b`, `two_sessions_get_their_own_dialogs`), 보인 것과 실제가 같음(`upload_shows_real_paths_and_uploads_the_bytes_shown`, `upload_origin_change_is_stale`, `a_storage_write_approved_after_the_tab_left_is_stale`, `a_cookie_approved_after_the_tab_left_lands_on_the_asked_host`), 명령이 끝남(시간 초과, 세션 닫기, 데몬 재시작, 응답자 사라짐), 초점(`the_dialog_does_not_take_focus`, 알림의 `giving_up_shows_a_notice_without_taking_focus`), 사람 프로필에 표시·숨기기 없음(`human_profiles_are_not_marked_or_hidden`).
- **C++ 변형**: 모든 C++ 변경에 변형 확인이 있다(작업 6~10 표). 작업 4(업로드)와 작업 7(확인 창)은 보안 검토를 따로 받았고, 작업 4는 재검토까지 받았다.
- **실제 브라우저 시험 전체** (두 번째 기기의 GUI 세션, spike-findings "3b 작업 11"): 포크 구성 `pegboard-core` 216 passed, 순정 구성 워크스페이스 전체 353 passed, 실패 0. 녹화가 명령에 더하는 시간(포크, 배포용 빌드) 명령별 중앙값 24~52ms(기준 60ms). 확인 창은 `confirm.required`에서 약 20ms 뒤에 뜬다.
- **업스트림 예산**: 3b의 손 패치 증가 **0줄**(목표 15줄 이하). 3a 끝과 같은 업스트림 파일 15개, 120줄(그중 45줄은 157 이상에서 지울 클립보드 패치). 새 UI는 모두 `//pegboard` 안이다(3b에서 +3,094줄, 지금 약 4,800줄). 생성 커밋(문자열)은 파일 165개, ±47,447줄로 따로 센다.
- 설계와 크게 달라진 곳: 확인 창이 시트(창 모달)가 아니라 자식 창(4.5), 버튼 잠금이 조용한 시간을 요구함(4.5), 고른 프레임에서의 쓰기·업로드는 묻지 않고 거부(4.4), 업로드 사본을 세션 끝까지 둠(4.3), 표시·숨기기를 도메인이 아니라 브라우저 시작부터(4.6), 시작 선택 화면은 생략이 아니라 Local State 기본값으로(4.6), 로그인 기본값을 설정 등록 때(4.6), 다른 앱의 링크가 사람 프로필로 가게 고침(4.6, 3a부터 있던 문제).

## 10. 열린 항목 (3c 이후)

3c(배포)에서 할 것:
- 키체인 `Pegboard Safe Storage` 확인 창: 새로 빌드하거나 다시 서명한 앱은 쿠키 저장소를 처음 열 때 묻고, 답할 때까지 모든 HTTP 요청이 멈춘다. 서명 ID가 고정되면 처음 한 번만이 될 것으로 본다 [미확인].
- 서명·공증, 그리고 제대로 서명한 빌드에서 `AperitifHelpers` 실험(도우미 프로세스의 샌드박스)이 네트워크를 막지 않는지. 지금은 `disable_fieldtrial_testing_config = true`로 피한다.
- 사람에게 줄 빌드는 `pegboard_test_hooks`를 켜지 않는다(`browser/args.gn`은 개발·시험용). 배포 빌드의 GN 인자를 따로 둔다.
- pegboard 홈과 브라우저 사용자 데이터 디렉터리 나누기(둘 다 `~/Library/Application Support/Pegboard`).

사람이 본 확인(2026-11-26)에서 나온 것:
- 확인 창에서 "거부"가 기본 버튼으로 구별되어 보이지 않고, 뜬 직후 잠긴 버튼도 흐리게 보이지 않는다. 잠금은 동작한다. 확인 창이 키 창이 아니어서 맥 views가 기본 버튼 강조와 비활성 모양을 그리지 않는 것으로 본다 [추정]. "거부"를 눈에 띄게(예: 강조 스타일을 직접 지정) 하고 잠긴 동안의 모양을 직접 그린다.

정하지 않은 것, 하지 않은 것:
- **`network` 확인** (B3): 넣지 않았다. 요청 가로채기를 에이전트에게 주면 데몬의 요청 가드와의 순서를 보장할 수 없다(2a 측정 D5: 에이전트 쪽 세션의 `Fetch.enable`이 가드의 차단을 7개 조합 중 5개에서 이겼다). 한 번의 클릭으로 사설망 차단이 열릴 수 있다. 가드가 늘 먼저 판정하게 하는 방법(예: 브라우저 쪽 패치로 가로채기 순서를 고정)을 찾기 전에는 넣지 않는다.
- 확인 창과 알림 문구의 번역(지금 한국어 하나, B14).
- 웹 UI의 로고 그림(설정 About 화면, `chrome://version`)은 Chromium 트리의 그림 그대로다. 두 대상 `.grd` 밖의 구글 문구("Google Chrome 도움말"처럼 `settings_strings.grdp`, `generated_resources.grd`에 있는 것)도 그대로다.
- 확인 창의 자리를 재지 않은 상태: 에이전트 창이 전체 화면이거나 다른 Space에 있을 때, 최소화되어 있을 때 사람이 어떻게 보는지.
- 위치를 정한 팝업 같은 다른 앞쪽 창이 확인 창을 가리는 것(8절), 손쉬운 사용 권한의 `AXPress`(8절).
- 확인 창이 떠 있는 동안 에이전트 창을 막을지(지금은 막지 않는다).
- 사람이 직접 볼 확인([phase3b-notes/manual-check.md](./phase3b-notes/manual-check.md)): 창의 모양과 읽기, 초점, Dock 튕김, 에이전트 창의 색과 제목, 프로필 메뉴, 설정 화면, About, 아이콘, 데몬 포기 알림. 결과를 spike-findings "3b 작업 11"에 적는다.

3a에서 이어지는 것(3b가 다루지 않았다):
- 저장된 탭그룹이 에이전트 프로필마다 쌓인다.
- 세션 관리자가 `runtimes` 뮤텍스를 쥔 채 프로필 창을 기다린다.
- 도메인에 프로필 지우기가 없다(`profile delete`는 데몬의 등록부에서만 지우고 Chromium 프로필은 남는다).
- 사람의 유일한 프로필을 지우면 에이전트 프로필로 넘어갈 수 있다(8절).
- `stopScreencast` 뒤 프레임 하나를 고정하는 시험, 1분 창 자체의 시험, 사람이 직접 준 `--remote-debugging-port`, 도메인 판 `createTab`의 첫 `navigated` 줄.
- `pegboard-cli` 시험 묶음 전체를 포크 구성으로 돌리기(녹화 지연 시험은 `PEGBOARD_TEST_BROWSER=fork:`로 포크에서 돈다. 나머지 CLI·MCP 묶음은 3b에서도 순정으로만 돌렸다).
- 시험이 남기는 agent-browser 데몬: 3b 끝의 전체 실행에서 구성마다 19개가 남았다(손으로 끔).
